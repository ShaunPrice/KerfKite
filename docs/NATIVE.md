# Native backend

Studio's compiled extension, `studio._relief_native`, is an in-process CPython extension built from the native core (`native/core/`) and three small files of its own: `studio/_relief_native.cpp` (the module and its functions), `studio/_core_native.cpp` (requests to the core and its answers as Python objects) and `studio/_gcode_native.cpp` (number text and packed preview rows). Through it the core computes Studio's G-code and rotary programs, reliefs, stock previews, probe levelling, circuit-board import, and the work of the polygon and solid kernels. Where a Python version exists, it stays as the reference that the core is compared with and as the fallback where the extension is not installed. There are no runtime compiler or subprocess calls, and the core runs without the GIL.

Install with a compiler and Python headers, then `python -m pip install .`. Developers can use `python -m pip install -e .`, which builds the extension in place with the setuptools release the project requires, or `python setup.py build_ext --inplace` where setuptools 77 or later is already installed (the release bundled with a new Python 3.10 environment is older and rejects the licence field). Windows uses MSVC `/O2 /fp:precise /std:c++17`; other builds use `-O3 -std=c++17 -ffp-contract=off -pthread`, without fast-math, and link `libdl` on Linux for the optional GPU library. The extension is optional, so inspect the backend rather than assuming compilation succeeded.

```python
from studio.relief import prepare_relief
result = prepare_relief(data)  # auto: native if importable, otherwise Python
print(result['surface']['backend'])  # cpp or python
reference = prepare_relief(data, backend='python')
accelerated = prepare_relief(data, backend='native')  # explicit error if absent
```

The UI identifies accelerated relief results. Restart an already-running server after installing the extension. Browser-only file mode does not load a CPython extension.

The first extension (September 2026) compiled only the relief's cutter contact; Python kept the settings, the work caps, the paths and the metadata. Its installed Pi medians were 1.142 s for the Python relief against 0.086 s in C++, and 2.864 s against 1.818 s for the whole calculation, about 37% less for that fixture; the installed Pi wheel passed ten relief tests, and six complete benchmark jobs gave the same G-code hash. C++ was chosen because its implementation was directly measured; no Rust performance comparison was made. Evidence: `validation/native-installed-pi5-2026-09-11.json` and `validation/native-installed-mac-2026-09-11.json`. The Mac evidence exercises the local compiled module; the Pi evidence imports from the temporary environment's installed site-packages. No persistent Pi service was deployed. The original standalone C++ executable remains only as a historical benchmark fixture.

## Relief finishing and the stock preview

`studio.relief.prepare_relief` and the stock preview (`studio.simulation.simulate`, behind `/api/simulate`) run in the native core (`native/core/src/relief.cpp`, `native/core/src/stock.cpp`), called through `core_cam` as the G-code is. The whole of each runs there, not only the arithmetic inside it:

* **The relief.** The settings and their messages; the height field, as rows of numbers or as the editor's RGB bytes in base64, read as strictly as the reference reads them and turned into luminance in numpy's order of arithmetic; the limits; the flat or ball cutter contact over the field; the raster paths and their depths; and the `surface` record saved with the design. The contact is shared out over threads or run on a GPU, as the next section describes.
* **The stock preview.** The settings, every segment row checked in the order the reference checks them, and the height map that the cutter leaves, computed row by row on the threads. The rows of a packed preview cross as bytes.
* **The same result, to the bit.** The relief's cell maxima are taken in the reference's order, with numpy's rules for an image and Python's `max` for rows of numbers. The stock preview's distances are CPython's `math.hypot` (`pymath::hypot` in `kerfkite/py_math.hpp`) and its minima are Python's `min`, which keeps the first of equal values; the extension's earlier stock kernel used the C library's `hypot` and differed from the reference in the last bits (by up to 2.7 × 10⁻¹⁴ mm on the 0.6.1 benchmark). A V-bit's slope is the C library's `tan`, which Python calls too, so the preview is Python's on each platform.
* **What the core declines.** A stock-preview row with text that is not a number raises `NotImplementedError` inside the call, and the Python reference answers it with its own message. The relief declines nothing.
* **What differs.** Where the result was computed: `device` is `cpu` or `gpu` from the core and `python` from the reference, and `surface.backend` is `cpp` or `python`. And the limits: with the core, image maps of up to 1024 points a side and jobs of up to 2 × 10⁹ contact checks; the Python reference keeps 256 and 10⁷.

```python
from studio.simulation import simulate
preview = simulate(data)                       # auto: the native core if installed, otherwise Python
reference = simulate(data, backend='python')   # the Python reference
core = simulate(data, backend='native')        # the core only: an error without the extension, and
                                               # NotImplementedError for what the core declines
```

`validation/native_core_parity.py` replays every relief and stock-preview call the test suite makes, and compares 1,500 generated reliefs (height fields of 2 to 40 points a side, as numbers and as image bytes, with settings from valid to invalid and base64 text that must be refused) and 1,500 stock previews of generated jobs, for every cutter. On Linux x86-64 (GCC 13, with Python 3.13 and with Python 3.12 under WSL) and on Windows (MSVC, Python 3.12) the results were the same: every generated case was reproduced (781 reliefs and 719 refusals, 771 stock previews and 729 refusals), and of the suite's calls one stock preview, of a row with text that is not a number, was declined. `tests/test_native_relief.py` compares the two for planes, ramps, domes, peaks, random fields, image maps, both cutter shapes, allowances, malformed input and the fallback path, and `tests/test_packed_cam.py` requires the core's stock previews for every cutter, with rows of every shape the reference accepts, to be the reference's bit for bit, and its refusals to be the reference's. The extension's former entry points for these (`contact`, `contact_packed`, `stock_heights`) and `studio/_stock_native.cpp` are gone. `kerfkite-cam relief` and `kerfkite-cam stock` run the same code without Python.

## Plans for manual tool changes

`studio.tool_changes.plan_tool_changes` and `/api/tool-changes` are answered by the native core as well (`native/core/src/tool_changes.cpp`, through `core_cam` and its text). The core reads the project as the reference does, with Python's equality between the operations' and the project's head, protocol and work area (numbers equal across `bool`, `int` and `float`, compared exactly), Python's truth for `rotary`, and tool names counted in characters and stripped of the characters `str.strip()` strips. It groups consecutive operations with the same tool and generates each stage as Studio generates an ordered job, so every stage carries the whole job, with the reference's number types. The route sends the core's JSON text. `validation/native_core_parity.py` compares 1,500 generated plans by default (runs of tools over lines, pockets, drilling and V-carving, with tool numbers, names, diameters, shapes and angles from valid to invalid, and projects the plan refuses) and the test suite's own; `tests/test_tool_changes.py` compares plans, refusals, the 200,000-line limit over all stages and the route.

## Fixture clearance

`studio.fixture_collision.check_fixtures` and `/api/fixture-collision` are answered by the native core too (`native/core/src/fixture_collision.cpp`). It reads the posted program line by line as the reference's generator does, so a refusal names the same first line, and the check of two million sweeps is made at the same move; each move is swept against each box with the reference's arithmetic (CPython's `hypot`, the C library's `sqrt`, Python's `min` and `max`), and the positions of the contacts are Python's `round(x, 5)`. A line that is not ASCII is declined: the reference reads it with Unicode's rules for case, spaces and digits. `validation/native_core_parity.py` compares 1,500 generated checks by default (generated programs with lines added or changed, boxes and setups from valid to invalid) and the test suite's own, and `tests/test_fixture_collision.py` compares checks, refusals and the route. The core's `round` now takes up to nine places; compared with Python on 12.9 million roundings from zero to nine places, it gave the same bits.

## Threads, and a GPU for large reliefs

The relief contact and the stock preview share their work out over the processor's threads. The split is fixed: rasters (relief) or rows of the height map (stock preview) go to the threads in equal runs, each value is written by one thread with the arithmetic of a single thread, and errors are found by a first pass in the order one thread would meet them. The number of threads therefore changes no bit of any result and no error message. A job starts a thread only for enough work (two million contact checks a thread, for the relief), and both release the GIL while they compute. `KERFKITE_THREADS=n` caps the threads; `1` runs everything on the calling thread.

With the compiled extension the relief takes larger maps: image height maps of up to 1024 points a side (256 without it) and jobs of up to 2 × 10⁹ contact checks (10⁷). The editor sends a map larger than 256 as the canvas's RGB bytes (`heightmap_rgb`, base64, with `heightmap_size` as columns and rows, top row first), from which the server computes the luminance the editor would have. `GET /api/session` reports the limit as `relief_map`. STL and artwork reliefs stay at 128, as their rasterisers are Python. A path still holds at most 100,000 points, so a 1024-point map needs a stepover of about a hundredth of the map's height or more.

### The GPU

A large relief may run on a GPU. KerfKite uses the OpenCL library that GPU drivers install, loaded when it is first needed: `OpenCL.dll` from the Windows system folder (and from nowhere else), `libOpenCL.so.1` on Linux, the OpenCL framework on macOS. Nothing of OpenCL is compiled in or shipped. The few functions used are declared from the public specification in `native/core/src/gpu/opencl.cpp`, behind the interface of `kerfkite/gpu.hpp`. Without the library or a suitable device, everything runs on the threads.

* **Which device.** With `KERFKITE_GPU=auto` (or unset), a discrete GPU with double precision. Integrated GPUs share the processor's memory and were measured slower than its threads, so they are left out. `KERFKITE_GPU=on` takes any device with double precision, a discrete GPU first, for tests and measurements; `off` uses none. The choice is made once per process.
* **The same bits.** The kernel is the contact arithmetic of `segment_contact` in `native/core/src/relief.cpp`, written out statement for statement in OpenCL C: double precision, no fused multiply-add, and maximum and minimum written to choose as `std::max` and `std::min` do. OpenCL requires double-precision division and square root to be correctly rounded, as they are on the processor. Each result is still checked: 128 of its contacts, the four corners among them, are computed again on the processor and compared bit for bit. On any difference the result is discarded, the job runs on the threads, and the GPU is turned off for the rest of the process.
* **When.** A job of fewer than 2 × 10⁸ checks stays on the threads, because its fixed costs on a GPU (buffers, transfers, launches) would take the gain. Setting a GPU up the first time in a process took 0.1 to 0.3 s, so large jobs run on the threads until they have spent that long there between them, or until one job alone is expected to; then the GPU is set up, and each later large job goes to whichever of the two has been measured faster. A single job on a processor with many cores thus stays on its threads, while a session of large reliefs moves to the GPU.
* **No driver resets.** Work goes to the device in slices that start at 64 contacts and grow to about 50 ms each, so no launch comes near the two seconds after which Windows resets a display driver, however slow the device is.
* **What it reports.** The editor says **C++ accelerated relief on the GPU** when a GPU computed the contact. The result's `device` is `gpu`, `cpu` or `python`; it is kept out of `surface`, which is saved with the design and is the same on every computer. `studio.relief.gpu_status()` names the device in use, or says why there is none.

Measured with `validation/benchmark_relief.py` on a laptop with an Intel Core Ultra 9 275HX (24 threads) and an NVIDIA GeForce RTX 5090 Laptop GPU (OpenCL 3.0, driver 617.71): a whole relief prepared from a synthetic RGB image of a 100 × 100 mm map with a ball cutter, from the image's base64 text to the paths and depths as Python objects, best of five (of six on one thread). The depths had the same digest in every way, under MSVC on Windows and on the GPU as under GCC on Linux. The 8 and 4 thread columns are the same processor with `KERFKITE_THREADS` capping it, standing for smaller processors.

| Job | Contact checks | 1 thread | 4 threads | 8 threads | 24 threads | GPU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 256-point map, 6 mm ball | 13.7 million | 29.7 ms | 17.2 ms | 14.8 ms | 15.0 ms | 12.7 ms |
| 1024-point map, 6 mm ball | 357 million | 476 ms | 148 ms | 97.3 ms | 71.3 ms | 60.6 ms |
| 1024-point map, 12 mm ball | 1.36 billion | 1.88 s | 482 ms | 267 ms | 140 ms | 127 ms |
| 1024-point map, 14 mm ball | 1.68 billion | 2.84 s | 730 ms | 391 ms | 174 ms | 156 ms |

Before the port, when the extension computed the contact and Python read the image and built the paths, the same benchmark took 97.8, 179 and 211 ms for the three large jobs on 24 threads and 97.6, 164 and 196 ms on the GPU: the port took 17 to 38 per cent off them there, and 5 to 24 per cent on 8 and 4 threads; the 256-point job did not change measurably. The contact alone, timed before the port through the extension's former entry point, was 40.8, 116 and 154 ms of the 24-thread times, so 20 to 30 ms of a large relief is reading the image and making the paths and their Python objects, mostly on one thread. Through `/api/relief` (`validation/benchmark_routes.py`), with the GPU off, a relief from the 1024-point image took 94 to 101 ms instead of 203 to 212 ms with the 6 mm ball, and 64 to 66 ms instead of 179 to 191 ms with a 1.1 mm ball, in four runs of each, because the core writes the response's JSON itself.

Setting the GPU up in a new process took 0.21 to 0.37 s in the runs measured, on top of the first job. Consumer GPUs run double precision at a small fraction of their single-precision rate, so on the large jobs the GPU was only 10 to 15 per cent faster than all 24 threads of this processor, but 1.6 to 2.5 times faster than 8 threads and 2.4 to 4.7 times faster than 4. The laptop's integrated GPU, measured with the prototype of the same kernel, took 1.52 s for a job of 1.37 billion checks that the 24 threads did in 0.17 s. The inner loop reads each cell edge from a table worked out once per job rather than multiplying it out at every check, which made one thread 19 to 25 per cent faster on these jobs with the same digests.

`tests/test_native_gpu.py` runs reliefs of several shapes with the GPU turned off, forced on and left to choose, each in a process of its own, and requires the GPU's depths to be the threads' bit for bit; without a usable GPU it says so and skips that comparison. `kerfkite_parallel_selftest` checks the split over threads and the runtime itself: a kernel's results equal the processor's bit for bit, a slice of work items that is not a multiple of 64 is handled, and a program that does not build turns the GPU off with the reason. The installed-wheel check runs a relief from a 400-point RGB map against a recorded digest, on the threads, on one thread and, where there is a GPU, forced onto it.

The stock preview stays on the threads. Its arithmetic is now the four operations, square roots and rounding to whole numbers, with CPython's `hypot` built from them and exact scaling by powers of two, and one `tan` for a job, so a GPU version could give the same bits; whether it would be faster has not been measured. The solid and polygon kernels make their decisions in exact integer arithmetic and do not use a GPU either.

## G-code and rotary output

Studio's G-code and rotary output come from the native core (`native/core/src/cam.cpp`, `rotary.cpp` and the files beside them), compiled into the extension and called through `core_cam` in `studio/_core_native.cpp`. `studio.cam.generate`, `studio.rotary.generate_rotary` and `studio.rotary.wrap_job` hand the request over and return the core's job; the Python modules behind them stay as the reference that the core is compared with, and as the fallback:

* **What crosses to the core.** A request goes to the core only when JSON would carry it unchanged: `None`, booleans, integers within 64 bits, finite floats, text, and lists and dicts with text keys, each of exactly that type. A tuple, a float subclass, a non-finite number or a key that is not text stays with the Python reference, which gives its own answer or message.
* **What the core declines.** The few cases it does not reproduce exactly (numbers written in non-ASCII digits, a contour whose self-crossing test turns on rounding inside GEOS, given G-code that is not ASCII) raise `NotImplementedError` inside the call, and the Python reference answers them.
* **The job is Studio's job.** The core gives every member the Python job has: the program lines, the preview segments with the reference's number types (the integer 0 of a laser move's height and of a beam-off gap), the cut length and time, bounds and warnings, the paths and depths cut, and for drilling the holes and the drill, or for an ordered job the number of operations. The job is built as Python objects directly from the C++ one, not written as text and read back, and the rows of the preview share the float objects of the points they have in common.
* **Previews as text.** The preview routes (`/api/generate` in both servers and `/api/rotary`) send the core's own JSON text of the job (`studio.cam.job_json`, `studio.rotary.rotary_json`), with names in byte order and numbers written as Python writes them, as Flask's `jsonify` would give them. For a large job that is most of the time of the request.

```python
from studio.cam import generate
from studio.rotary import generate_rotary
job = generate(project)                            # auto: the native core if installed, otherwise Python
reference = generate(project, backend='python')    # the Python reference
core = generate(project, backend='native')         # the core only: an error without the extension, and
                                                   # NotImplementedError for what the core declines
rotary = generate_rotary(project, options, backend='python')
```

`KERFKITE_GCODE_BACKEND=python` in the server's environment makes `auto` use the Python CAM without reinstalling, and so does `KERFKITE_POLYGON_BACKEND=shapely`, since only the Python CAM can take offsets, pockets and fills from Shapely. The core runs without the GIL.

**The output is identical, not merely close.** The core writes fixed-point text with exact integer arithmetic, rounding half to even on the exact binary value as Python does; squares use the same `pow` call that Python's `**` makes; `math.dist`, `sum()` and `math.hypot` are reproduced step for step as CPython 3.12 computes them (`kerfkite/py_math.hpp`); and the rotary post's `asinh` is the C library's, which is what CPython 3.11 and later call. `validation/native_core_parity.py` compares the core with the Python reference on every generator and rotary call the test suite makes, on 20,000 generated projects, 6,000 ramp, helix and tab jobs, 5,000 helical pockets, 4,000 V-carves, and 3,000 rotary jobs with 1,500 given programs, on Linux, macOS, Windows and ARM in CI: every case is reproduced or declined.

`tests/test_native_gcode.py` compares the two for router, relief, laser, perforated and bridged jobs, in list and packed forms, with number types and every member of the job; drilling, ordered, ramp, pocket and knife jobs; what may cross to the core and what stays with the reference; the environment switches; the JSON text; 96 rotary option combinations, the rotary limits and given programs. `validation/benchmark_gcode.py` times the Python reference against the core and fails if their program hashes differ.

The extension keeps two small pieces of its own here (`studio/_gcode_native.cpp`): unpacking packed preview rows at the JSON boundary, and the core's fixed-point text and `round()`, which the tests compare with Python's formatting. The per-move loops and the rotary run translator it had before, written for the Python generator, are gone: the core generates the whole job.

## Python-free core

`native/` holds the start of the application's move to C++: a C++17 library and the `kerfkite-cam` command-line tool, which write G-code from a project file with no Python installed. It currently reproduces router line jobs, laser line jobs (leads, power ramps, perforation, holding bridges and raster powers), drilling, drag-knife paths, inside and outside offsets, pockets, hatch fills, V-carving, ramp entries, helical entries into pockets, holding tabs, ordered multi-operation jobs and controller post-processing: every operation of a job. What it cannot reproduce exactly (a number written in non-ASCII digits, a contour whose self-crossing test turns on rounding inside GEOS) is declined, never approximated. It contains no third-party code and its build downloads nothing. `native/README.md` lists what is ported and how to build it.

Probe levelling (`native/core/src/leveling.cpp`) is the first part of the application written only in the core: it has no Python version. The extension compiles that file and exposes it as `core_call`, which `studio/leveling.py` wraps; the extension is therefore built as C++17 and compiles the core's JSON reader and writer with it. See [Probe levelling](PROBE-LEVELING.md).

Circuit board import (`gerber.cpp`, `excellon.cpp`, `pcb.cpp`) is written the same way, compiled into the extension and wrapped by `studio/pcb_import.py`. So are isolation toolpaths (`isolation.cpp`), for which the extension also compiles the polygon kernel (`polygon/`). See [Circuit boards](PCB.md).

Offsets, pockets, hatch fills and V-carving are computed by the core's own polygon kernel (`native/core/src/polygon/`, `native/core/src/operations.cpp`, `native/core/src/vcarve.cpp`; see [The polygon kernel](POLYGON-KERNEL.md)). This is the third part with a single implementation: the extension compiles the kernel and the operations, and `studio/operations.py` calls them through `core_call` after checking the job's settings in Python, so Studio and `kerfkite-cam` cut the same paths by construction. GEOS, which the core built for these operations at first, has been removed from the native build with its options.

```python
from studio import operations
operations.polygon_backend()   # 'kernel' with the extension, 'shapely' without it
```

Without the extension (the portable wheel) the same operations run on Shapely, as they did before the kernel. The fallback cuts the same regions, but its vertices are not the kernel's: arcs are approximated from inside the true arc and not from outside, rings start elsewhere, pockets have many more vertices, a contour that closes only to within the tolerance is usually refused, and a V-carve is written as one path for each piece of the diagram, in no particular order. `KERFKITE_POLYGON_BACKEND=shapely` selects the fallback where the extension is installed, and `=kernel` refuses to run without the extension. Kernel coordinates are whole millionths of a millimetre; each crosses the JSON boundary as the shortest text of the double `n / 1e6` and is read back as exactly that double, which `tests/test_polygon_operations.py` checks.

`validation/check_installed_cam.py` pins these operations on every platform a wheel is built for: an inside offset, an outside offset, a pocket and a cross-hatch fill at 33.3 degrees, generated through the installed extension, must give the recorded digest, and so must the paths, depths and program of a V-carve (a slanted outline with an island and a block letter, 13,320 points). On Linux x86-64 the extension (GCC 13) and `kerfkite-cam` built with GCC 13, with Clang 18 and with the address and undefined-behaviour sanitizers wrote the same four programs.

Solid modelling is the fourth part computed by the core for Studio. The extension compiles the solid kernel (`native/core/src/solid/`, `solid_command.cpp`) and the polygon kernel's own command (`polygon/command.cpp`), and `studio/solid_kernel.py` gives them the interface Studio's 3D CAD modules call: parts, CAD scripts and their 2D drawings, lofts, STEP tessellations and assemblies. Unlike the operations above, a model is built in many steps, so the extension has a second entry beside `core_call`: `solid_call(request, kept)` answers with the JSON and with the solid itself, which Python keeps and passes back to later requests, so no mesh crosses as text between steps. `solid_mesh(solid)` gives the mesh of a kept solid as bytes for numpy.

```python
from studio import solid_kernel
solid_kernel.solid_backend()   # 'kernel' with the extension, 'manifold' without it
```

Without the extension the same modules model with the third-party library manifold3d, as before. `KERFKITE_SOLID_BACKEND=manifold` selects it where the extension is installed, and `=kernel` refuses to run without the extension. The two give the same shapes within nanometres, except where they facet differently (spheres, round offsets, twisted extrusions), and the kernel is slower, by a factor of 2 to 6 on most parts. When the kernel refuses a result as too fine for its grid, Studio reports the error; it never switches library for one model. [The solid kernel](SOLID-KERNEL.md#how-studio-uses-the-kernel) has the details and the measurements.

`validation/check_installed_cam.py` pins this too: a part of seven features and a drawing, modelled through Studio's entry points with the installed extension, must give the recorded digest of every vertex, triangle and outline. On Linux x86-64 the extension built with GCC 13, with Clang 18, and with the portable 128-bit integers a compiler without a 128-bit type uses, gave the same digest. Windows (MSVC), macOS and ARM64 builds have not been run; the check is what tests them.

The exact number formatting described above now lives in one header, `native/core/include/kerfkite/number_text.hpp`, used by both the Python extension and the core.

The core reads and writes JSON with its own code (`native/core/include/kerfkite/json.hpp`, `native/core/src/json.cpp`), which replaced the vendored JSON for Modern C++ header; the core has no third-party source. It supports what the core uses: all of RFC 8259 on input, with every escape and surrogate pairs; numbers that keep their kind, so that `1` stays a whole number and `1.0` a float as the Python reference requires; objects with their names in byte order, the last value standing where a name repeats; and one-line output. Its limits: arrays and objects nest at most 200 deep in text that is read, text must be well-formed UTF-8 in both directions, a literal beyond the range of a double is refused, and there is no indented output, comment syntax or binary format. A float is read as the nearest double and written as the shortest text that reads back as the same double, by exact integer arithmetic in `native/core/include/kerfkite/decimal.hpp`; the C library's conversions and the C locale are not involved, and `repr` in `number_text.hpp` and `float()` of text in a project use the same code. Floats are therefore written as Python writes them. The old library wrote two things differently: a float from 1e15 up to 1e16 in exponent form (`1e+15`, now `1000000000000000.0`), and, for roughly one double in a thousand, digits that were not the shortest (`23.343139999999998`, now `23.34314`). Both forms read back as the same double.

It was checked on Linux x86-64 (GCC 13 and Clang 18) in four ways. `native/tests/json_selftest.cpp`, which CTest runs on every platform, covers each construct, the number kinds, the limits and malformed input, holds tables of doubles computed by Python, and compares every short cut in the number conversions with the exact arithmetic behind it on some 300,000 doubles and the decimals written from them. Against Python, 5 million decimal texts (ties between doubles, decimals one digit either side of a tie hundreds of places along, subnormals, exponents far outside the range) gave the double `float()` gives, and 5 million doubles gave the text `repr()` gives, with the short cuts and without them. Against the library it replaced, while that was still in the tree, 440,000 documents (generated, damaged at random, and real: fixtures, projects recorded from the test suite and the answers to them) were read by both: the same were accepted and refused, with the same values, kinds and order; equality between 87,000 pairs of values agreed; and the 26,215 jobs of the parity comparison below gave answers equal in every value and type, 97.7% of them byte for byte, the rest differing only as described above. The one deliberate difference in what is accepted, apart from the depth limit, is that text after a NUL byte is refused, where the old library stopped reading at the NUL. Under the address and undefined-behaviour sanitizers, the self-tests, 500,000 mutated documents, the comparison corpus and 2,500 jobs through `kerfkite-cam` ran without a report. Windows (MSVC), macOS and ARM64 builds have not been run; the self-test is the check for them.

`python validation/native_core_parity.py --cli <kerfkite-cam>` compares the core with the Python reference: number text, every generator call the test suite makes, and thousands of generated edge cases. A case must be reproduced exactly or declined; a different answer fails. With laser jobs ported, the measurement on Linux x86-64 is: 300,000 numbers and 360,000 distances and sums identical; 124 of 202 recorded suite calls reproduced (61%); 11,225 of 12,000 generated cases reproduced (94%), among them 1,137 laser programs; and no differences. The three benchmark programs written by `kerfkite-cam` have the same hashes as Python's.

Drilling (`native/core/src/drilling.cpp`) and drag-knife paths (`native/core/src/knife.cpp`) are ported as well. The generated cases gained 4,000 drilling and knife projects. On Linux x86-64, with those two parts: 160 of 205 recorded suite calls reproduced (78%, from 62%); 15,562 of 16,000 generated cases reproduced (97%), among them 1,290 drilling and 1,634 drag-knife programs; and no differences. The one knife case declined then was a path that returns to a point through steps too short to keep, where the Python divided by zero. That was a defect in the reference: it compared each point with the one before it in the drawing, kept or not. Both now keep a point only when it is further than 0.1 nm from the last point kept, and refuse a path that is then a single point, so the core reproduces every knife job and declines none. Knife swivels use the platform's `atan2`, `sin` and `cos`, as Python does, so they are compared on each platform against the Python there.

Ramp entries and holding tabs on router line jobs are reproduced too (`native/core/src/router_entry.cpp`, `tabs.cpp`). Before either, the reference asks Shapely whether each contour crosses itself; `simple_line.cpp` answers by the rules GEOS applies, including its double-double orientation test, and declines the rare contour for which that test and exact arithmetic disagree. A helix entry needs a pocket, so on a line job it is rejected as the reference rejects it. The ramp slope is `math.tan` of the entry angle, one C library call on each side. With these ported, the measurement on Linux x86-64 is: 161 of 205 recorded suite calls reproduced (79%); 11,432 of the same 12,000 generated cases (95%); and 5,951 of 6,005 ramp, helix and tab cases, among them 3,254 programs, the rest of those declined because they also ask for an offset, a pocket or drilling; no differences.

Helical entries into pockets are reproduced as well (`native/core/src/router_entry.cpp`). The reference placed each helix with Shapely: the pocket's region, two insets of it, the nearest point of an inset to the first point of each pass, a distance to the boundary and a covering test for the feed from the helix to the pass. The vertices of a GEOS inset cannot be reproduced to the last bit by other code, so this part was moved instead, as the offsets and pockets were: `native/core/src/pocket_entry.cpp` places the helix on the core's own polygon kernel by the same rules, the extension exposes it as the `helix` operation of `core_call('operation', ...)`, and `studio/router_entry.py` calls it through `studio.operations.kernel_pocket_entries` whenever the extension is installed. Studio and `kerfkite-cam` therefore place the same helix by construction, and the Shapely code remains as the fallback without the extension (or with `KERFKITE_POLYGON_BACKEND=shapely`). The centre of a helix is a double worked out with `+ - * /` alone, the same on every platform; the start angle is the platform's `atan2`, and the helix points its `sin` and `cos`, as in Python. The move also put right a fault that came with the kernel's pockets: Studio had been checking the kernel's passes, which lie on a grid of a millionth of a millimetre, against a Shapely inset to a hundredth of that, and refused most pockets with walls at an angle.

That the cutter stays clear is checked independently of both codes. `tests/test_router_entry.py` generates pockets of many shapes, with and without islands, and measures with Shapely the distance from every cutter position of the job to the contours as drawn: the centre of each helix is at least the cutter radius plus the helix radius from every wall, with no tolerance, and the feeds and passes are within 0.000002 mm of the cutter radius, the two half steps of the kernel's grid. The core's self-test makes the same check on generated pockets with a distance function of its own and compares a digest of the centres with a recorded value, and `validation/check_installed_cam.py` pins the centres an installed wheel gives.

With these, and with the drag-knife fix, the measurement on Linux x86-64 (GCC 13, Python 3.13) is: 368 of 369 recorded suite calls reproduced (219 programs and 149 rejections; the one declined is V-carving); 19,986 of 20,000 generated cases; all 6,005 ramp, helix and tab cases; and 4,998 of 5,004 pockets entered by a helix, a new group (2,189 programs and 2,809 rejections; the six declined are untidy cases whose operation was replaced with V-carving). Nothing differs, and V-carving is the only feature declined (21 cases in all).

V-carving is reproduced too, and with it every operation of a job (`native/core/src/vcarve.cpp`). The reference sampled the outlines, took Shapely's Voronoi diagram of the samples, cut it to the region and measured each point's distance to the walls. The vertices of a GEOS diagram cannot be reproduced to the last bit by other code, so this part was moved as the offsets and the helix were: the polygon kernel gained its own Delaunay triangulation and Voronoi diagram of points (`native/core/src/polygon/voronoi.cpp`: divide and conquer in O(n log n), the side-of-line test exact in 128 bits and the in-circle test in 256, vertices worked out as exact fractions and rounded to the grid, halves upwards) and the distance from a point to a region's boundary; the carve is built on them; the extension exposes it as the `vcarve` operation of `core_call('operation', ...)`; and `studio/operations.py` calls it through `kernel_vcarve` whenever the extension is installed. The Shapely code remains as the fallback without the extension (or with `KERFKITE_POLYGON_BACKEND=shapely`). The method, its allowance of one sampling interval, the settings, their limits, the messages and the warning are the reference's. What the kernel adds is a defined result: samples from each ring's smallest vertex, coordinates on the grid, pieces that share an end joined into longer paths, and the paths in an order with little travel. Nothing in a carve comes from the C library but `sqrt`; the tangent of the bit's half angle is the kernel's own series. A carve of more points than a job may hold (200,000) is refused in the core with the generator's message, without being built. [The polygon kernel](POLYGON-KERNEL.md#v-carving) has the rules and the measurements.

That the bit never cuts outside the outline is checked independently of both codes. At every point of every path the circle the bit cuts at that depth, of radius `|z| tan(angle / 2)`, must be at least the sampling interval short of the nearest wall, and in the middle of every move it must still be short of the wall; the point must be in the region, and the depth within the depth of cut and the tool's radius. `tests/test_vcarve.py` and `validation/vcarve_check.py` measure this with Shapely on generated shapes (words of block letters, shapes with holes, thin strokes, flat areas, round shapes, stars), the core's self-test measures it with a distance function of its own and compares a digest of the carves with a recorded value, and `validation/check_installed_cam.py` pins the carve an installed wheel gives. The same scripts compare the carve with Shapely's carve of the same samples, which it follows to nanometres.

With V-carving, the measurement on Linux x86-64 (GCC 13, Python 3.13) is: all 370 recorded suite calls reproduced (221 programs and 149 rejections); all 20,000 generated cases (9,737 programs and 10,263 rejections); all 6,005 ramp, helix and tab cases; all 5,004 pockets entered by a helix; and all 4,010 V-carves, a new group (2,366 programs and 1,644 rejections). Nothing differs and nothing is declined: in this run every case was reproduced. The core can still decline an input, never an operation: a number written in non-ASCII digits or beyond the range of a double, a contour whose self-crossing test turns on rounding inside GEOS or passes the bound on work, and a few degenerate contours under tabs and ramps. `validation/vcarve_check.py` on 4,000 generated projects carved 2,287 shapes: at every point the cut was at least 1.0000 sampling intervals short of the nearest wall and in the middle of every move at least 0.5082; against Shapely's carve of the same samples no point of either carve was further than 2.2 nm from the other and the total lengths agreed to 2.1 parts in a million. `kerfkite-cam` built with GCC 13, with Clang 18, with the kernel's own 128-bit integer throughout (the one a compiler without a 128-bit type uses) and under the address and undefined-behaviour sanitizers gave the same bytes for 1,114 generated jobs, 810 of them V-carves, and each build passed the self-tests with their recorded digests. Windows (MSVC), macOS and ARM64 builds have not been run; the digests in the self-tests and the installed-wheel check are what test them.

The test of whether a contour crosses itself (`native/core/src/simple_line.cpp`) has a bounded worst case. It used to apply GEOS's test to every pair of segments whose bounding boxes overlap. For a contour of long segments side by side that is every pair: a comb of 20,000 parallel strokes took 2.1 s and one of 100,000, the most a job may hold, about a minute; a fan of rays and a square spiral behaved alike. (A contour that does cross was never slow: the first crossing found ends the test.) Two things bound it now.

* A tree over the segments, walked two branches at a time. A pair of branches is left out whole when GEOS's test is certain to pass every pair of segments in it: when the boxes of the two branches are apart, or when every end point in one branch is clear of, and on one side of, the line of every segment in the other. The second holds because GEOS passes two segments as soon as its orientation test puts both ends of one strictly on one side of the other, and that test is exact whenever its floating-point filter settles the sign; the tree asks for three times the margin the filter needs, at every corner of the boxes of end points, and the determinant is of the first degree in each coordinate, so the corners bound it. The branches are split on whichever coordinate of the segments' first or second end points is most spread, which keeps those boxes small for combs, fans and spirals alike. The same contours of 100,000 segments now take 0.05 to 0.12 s.
* A count of the work, in fixed units of a few nanoseconds each. Past 400 million units, about a second, the contour is declined as not ported. The count does not depend on the machine, so the tests bound it without timing anything: the self-test requires a multiple of n log n for long simple lines of five kinds, and that a contour past a small budget is declined at once.

The answer is unchanged. `validation/native_core_parity.py` compares it with Shapely's `is_simple` for 20,000 lines by each of three methods (the usual one, the tree forced on short lines, and every pair): points on coarse grids, random points, points in a line, and regular lines of 50 to 400 points spoilt by one touch, crossing, overlap, repeated vertex or a vertex a few units in the last place off another segment, with strokes from far apart down to a few units in the last place apart. A further 400,000 lines from other seeds were compared the same way while this was written. The tree and the test of every pair meet the pairs in different orders, so on the rare contour whose answer depends on rounding inside GEOS one may decline where the other answers; where both answer they agree.
