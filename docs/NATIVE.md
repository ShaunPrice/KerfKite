# Native backend

KerfKite's CAD, CAM and machine work is done by one C++17 library, the native core (`native/core/`), and the programs built on it: the workstation server `kerfkite-studio`, the HTTPS editor `kerfkite-web`, the MCP assistant server `kerfkite-mcp`, the command-line tool `kerfkite-cam` and the STEP add-on `kerfkite-step` (`native/server/`, `native/tools/`, `native/step/`; [the native programs](../native/README.md) shows how to build and run them). Windows builds use MSVC `/O2 /fp:precise /std:c++17`; other builds use `-O3 -std=c++17 -ffp-contract=off -pthread`, without fast-math, and link `libdl` on Linux for the optional GPU library. There are no runtime compiler calls.

The core was ported from Studio's Python implementation, which stayed in the tree as its reference until Studio 0.7 removed it. This page records how each part reproduces that reference, how the two were compared, and the rules by which the core differs on purpose. The Python modules and tests it cites (`studio/*.py`, `tests/test_*.py`), the compiled extension through which the Python called the core (`studio._relief_native`), and the comparison harnesses it names (`validation/native_core_parity.py` and the others) are those of the last commit that had the reference. Continuous integration checks that commit out and runs its comparisons against every build ([The Python reference](DEVELOPER.md#the-python-reference)). Where the page says that the reference, Shapely, manifold3d or "the Python" answers or falls back, it describes that commit. The programs answer every request with the core alone, by its own rules.

The first extension (September 2026) compiled only the relief's cutter contact; Python kept the settings, the work caps, the paths and the metadata. Its installed Pi medians were 1.142 s for the Python relief against 0.086 s in C++, and 2.864 s against 1.818 s for the whole calculation, about 37% less for that fixture; the installed Pi wheel passed ten relief tests, and six complete benchmark jobs gave the same G-code hash. C++ was chosen because its implementation was directly measured; no Rust performance comparison was made. Evidence: `validation/native-installed-pi5-2026-09-11.json` and `validation/native-installed-mac-2026-09-11.json`.

## The core's own rules

Where the Python reference answers a request by rules the core does not share (a repair pypdf makes, a quirk of Python's tokenizer, a decision GEOS's rounding could take either way, a limit of a library's), the core answers by rules of its own, and notes that it did (`own_rule`, in `core/include/kerfkite/cam.hpp`). The programs answer so. The reference's rules are kept for the comparison: with them in force (`set_reference_rules(true)`, which the extension set when it loaded), each such case is declined, as the Python service, which answered it with its reference, needed. The rules are, by part:

* **Whether a contour crosses itself** (`simple_line.cpp`): the exact orientation where GEOS's double-double arithmetic would give another sign, in integers where coordinates are below 10⁻¹⁴⁰ or above 10¹⁴⁰ in size; a contour whose test needs more work than about a second is refused (**A contour is too complex to test whether it crosses itself; simplify it or split it**); a length within rounding of a limit is decided by the core's sum.
* **Numbers** (`project.hpp`): a JSON number beyond the range of a double is an infinity, which every bound refuses, where the reference's `float()` of a Python int raised OverflowError. Coordinates written with fixed decimals and placements rounded by `round()` are exact for every double (`text::fixed_exact`, `text::rounded_exact`).
* **DXF** (`dxf.cpp`): a repeated fit point is passed through once and a zero end tangent leaves the ends free, where the reference cannot interpolate; an XCLIP boundary's validity is decided exactly; nested windows beyond the polygon kernel's range are refused. Splines given only by fit points are no own rule: the core interpolates them as the reference does (below).
* **Surfaces** (`surface.cpp`): an outline whose loops touch is refused like one whose loops cross (**Use a simple outline with non-overlapping holes inside it**), where Shapely allows a touch at a point.
* **Parametric solids** (`solid_cad.cpp`): a dimension expression outside the grammar the core reads (powers, floor division, other characters and keywords, tuples, calls of calls) is refused with the reference's message for a construct it does not evaluate, **Use numbers, named parameters, parentheses and + − * / in dimensions**, and one that does not parse with **Invalid dimension expression**; a sketch's area within rounding of the limit is decided by the core's area; solid features of kind step are refused by `kerfkite-cam`, which has no Open CASCADE (the server's STEP add-on meshes them).
* **PDF pages** (`pdf_import.cpp`): what the PDF format says (escapes in names and strings, a reference to an object that is not there being the null object, hybrid cross-references, inline images skipped to their `EI` and counted as images), repairs readers commonly make (a stream's length found from its `endstream`, `startxref` found by searching, cross-reference entries of a looser form, data decoded as far as it goes and filters' data without their end markers), refusals with the reference's messages for any encrypted file and for what cannot be read (**Cannot read this PDF page. Export a simplified, unencrypted vector PDF.**), and limits of the core's own below pypdf's.
* **LightBurn bundles** (`bundle_import.cpp`) need none: their unusual archives are read as Python 3.13 reads them, and what zipfile cannot open is refused as an unreadable bundle (see below).

`kerfkite-cam batch` keeps the reference's rules, for the parity comparison; `kerfkite-cam batch --own` answers by the core's own rules and names them in each answer (`"own": [...]`). `validation/native_core_parity.py` puts every case it declined with the reference's rules to the core again with its own, which must answer each as a program or a refusal. Started with `KERFKITE_PARITY=1`, the server names the own rules it answered a request by in an `X-KerfKite-Own-Rule` header, which `validation/server_route_parity.py` counts apart. Since the Python reference was removed in Studio 0.7, the core's rules are Studio's.

## Relief finishing and the stock preview

Relief finishing (`/api/relief`) and the stock preview (`/api/simulate`) run in the native core (`native/core/src/relief.cpp`, `native/core/src/stock.cpp`), the ports of the reference's `studio.relief.prepare_relief` and `studio.simulation.simulate`. The whole of each runs there, not only the arithmetic inside it:

* **The relief.** The settings and their messages; the height field, as rows of numbers or as the editor's RGB bytes in base64, read as strictly as the reference reads them and turned into luminance in numpy's order of arithmetic; the limits; the flat or ball cutter contact over the field; the raster paths and their depths; and the `surface` record saved with the design. The contact is shared out over threads or run on a GPU, as the next section describes.
* **The stock preview.** The settings, every segment row checked in the order the reference checks them, and the height map that the cutter leaves, computed row by row on the threads. The rows of a packed preview cross as bytes.
* **The same result, to the bit.** The relief's cell maxima are taken in the reference's order, with numpy's rules for an image and Python's `max` for rows of numbers. The stock preview's distances are CPython's `math.hypot` (`pymath::hypot` in `kerfkite/py_math.hpp`) and its minima are Python's `min`, which keeps the first of equal values; the extension's earlier stock kernel used the C library's `hypot` and differed from the reference in the last bits (by up to 2.7 × 10⁻¹⁴ mm on the 0.6.1 benchmark). A V-bit's slope is the C library's `tan`, which Python calls too, so the preview is Python's on each platform.
* **Text and padding.** A stock-preview row with text `float()` cannot read is refused with `float()`'s own message, `repr()` and all, and text in digits of other scripts is read as `float()` reads it. Base64 text that is whole groups followed by nothing but `=` is refused, as Python 3.12.10 and 3.13 refuse it (3.11.18 and 3.12.3 decoded the groups and ignored the `=`). The relief and the stock preview decline nothing.
* **What differs.** Where the result was computed: `device` is `cpu` or `gpu` from the core and `python` from the reference, and `surface.backend` is `cpp` or `python`. And the limits: with the core, image maps of up to 1024 points a side and jobs of up to 2 × 10⁹ contact checks; the Python reference kept 256 and 10⁷.

`validation/native_core_parity.py` replays every relief and stock-preview call the test suite makes, and compares 1,500 generated reliefs (height fields of 2 to 40 points a side, as numbers and as image bytes, with settings from valid to invalid and base64 text that must be refused) and 1,500 stock previews of generated jobs, for every cutter. On Linux x86-64 (GCC 13, with Python 3.13 and with Python 3.12 under WSL) and on Windows (MSVC, Python 3.12) the results were the same: every generated case was reproduced (781 reliefs and 719 refusals, 771 stock previews and 729 refusals), and of the suite's calls one stock preview, of a row with text that is not a number, was declined. `tests/test_native_relief.py` compares the two for planes, ramps, domes, peaks, random fields, image maps, both cutter shapes, allowances, malformed input and the fallback path, and `tests/test_packed_cam.py` requires the core's stock previews for every cutter, with rows of every shape the reference accepts, to be the reference's bit for bit, and its refusals to be the reference's. The extension's former entry points for these (`contact`, `contact_packed`, `stock_heights`) and `studio/_stock_native.cpp` are gone. `kerfkite-cam relief` and `kerfkite-cam stock` run the same code without Python.

## Plans for manual tool changes

`studio.tool_changes.plan_tool_changes` and `/api/tool-changes` are answered by the native core as well (`native/core/src/tool_changes.cpp`, through `core_cam` and its text). The core reads the project as the reference does, with Python's equality between the operations' and the project's head, protocol and work area (numbers equal across `bool`, `int` and `float`, compared exactly), Python's truth for `rotary`, and tool names counted in characters and stripped of the characters `str.strip()` strips. It groups consecutive operations with the same tool and generates each stage as Studio generates an ordered job, so every stage carries the whole job, with the reference's number types. The route sends the core's JSON text. `validation/native_core_parity.py` compares 1,500 generated plans by default (runs of tools over lines, pockets, drilling and V-carving, with tool numbers, names, diameters, shapes and angles from valid to invalid, and projects the plan refuses) and the test suite's own; `tests/test_tool_changes.py` compares plans, refusals, the 200,000-line limit over all stages and the route.

## STL height fields

The height field of an STL relief, ported from the reference's `studio.mesh_import.stl_heightmap`, is made in the native core too (`native/core/src/stl_heightmap.cpp`). It reads a binary file when its record count matches its length and an ASCII file otherwise, as the reference does: the ASCII lines split and stripped by Python's rules, the `solid` and `endsolid` lines and each facet matched as the reference's regular expressions match them, in either case, and every number read as `float()` reads it. Base64 text of whole groups followed by nothing but `=`, which some Python releases read and others refuse, was declined to the Python in use; the core refuses it, as Python 3.12.10 and 3.13 do. The triangles are normalised to the mesh's bounds with Python's `min` and `max`, clipped to each raster cell with the reference's arithmetic, and the cells raised to the highest point clipped to them, with the same work limit. A mesh of 10,082 triangles at resolution 128 took 15 ms in the core and 483 ms in Python on a two-core test machine, with the same height field. `validation/native_core_parity.py` compares 1,000 generated meshes by default (binary and ASCII, at every resolution, with the spellings, spacing and line breaks ASCII files have, and damaged in the ways the reader must refuse), and `tests/test_mesh_import.py` compares meshes, refusals and the work limit.

## Artwork reliefs

`/api/artwork-relief` turns closed artwork contours into a raised or recessed relief in the native core (`native/core/src/artwork_relief.cpp`), and `kerfkite-cam artwork-relief` does the same without Python. Each sample of a grid of 16 to 128 points stands for a cell reaching one grid step to each side. A raised relief keeps material at a sample whose cell meets the artwork, its outline included. A recessed relief keeps it where the artwork does not cover the whole cell. The height field of 0s and 1s then goes through the core's `prepare_relief`, and the route adds its warning.

This is the first route that the core answers on KerfKite's own geometry rather than the reference's, so the core is now the one implementation of the rasteriser. The artwork is the polygon kernel's even-odd region of the contours, built by the same code as offsets and pockets, with the reference's messages for open, self-crossing, zero-area and cancelling contours. Every cell is placed on the kernel's grid of a millionth of a millimetre. A cell meets the artwork when an edge of the region meets the closed cell or its centre is inside, and is covered when no edge enters the open cell and its centre is inside. Both are decided with exact integer arithmetic. The settings are read in the reference's order, with its messages. The Shapely version in the reference's `studio/artwork_relief.py` was its reference, and answered where the extension was missing.

The answers can differ from Shapely's in two places. One is a cell whose edge lies within a millionth of a millimetre of the outline: the kernel holds both at the same grid point, while Shapely compares doubles that differ in their last bits. The other is where contours cross one another and GEOS rounds the crossing points. `validation/artwork_relief_check.py` compares the two on generated artwork: rectangles, many of them with their edges on cell edges, turned rectangles, polygons standing for circles, stars, outlines with holes, and contours that cross. On 500 cases of two seeds, with 1,862,733 cells, 2,808 cells differed. Every one of them lay within two millionths of a millimetre of the outline, and the core kept material at 1,315 of them, so neither answer is consistently the more cautious. Every refusal was the reference's. The core rasterised them in 0.14 s, Shapely in 14.7 s. `tests/test_artwork_relief.py` checks that cells away from the outline agree, that refusals and the route match the reference, and that the Python CAM fell back to Shapely.

## Fixture clearance

`studio.fixture_collision.check_fixtures` and `/api/fixture-collision` are answered by the native core too (`native/core/src/fixture_collision.cpp`). It reads the posted program line by line as the reference's generator does, so a refusal names the same first line, and the check of two million sweeps is made at the same move; each move is swept against each box with the reference's arithmetic (CPython's `hypot`, the C library's `sqrt`, Python's `min` and `max`), and the positions of the contacts are Python's `round(x, 5)`. A line that is not ASCII is read with Python's rules for case, spaces and digits: it is upper-cased as `str.upper()` does, split at any space `str.split()` splits at, its digits of other scripts are numbers as `\d` and `float()` take them, its length is counted in code points, and a message names its words upper-cased. `validation/native_core_parity.py` compares 1,500 generated checks by default (generated programs with lines added or changed, boxes and setups from valid to invalid) and the test suite's own, and `tests/test_fixture_collision.py` compares checks, refusals and the route. The core's `round` now takes up to nine places; compared with Python on 12.9 million roundings from zero to nine places, it gave the same bits.

## Parametric solids

The front end of Studio's 3D CAD is moving into the native core too, starting with the parametric solid history (`native/core/src/solid_cad.cpp`, the port of `studio/solid_cad.py`). `/api/solid-cad` and `/api/solid-cad/section` are answered by the core, and `kerfkite-cam solid-cad` and `solid-cad-section` rebuild a model without Python. The port reproduces the following:

* the model's checks and messages, in the reference's order;
* named parameters, resolved in the order of the model's dictionary;
* dimension expressions: numbers written as Python writes them, names, `+ - * /`, signs, parentheses, and `cross_x` / `cross_y`, with Python's counting of the expression's nodes for the limit of 48;
* boxes, cylinders and spheres, turned and placed;
* sketched extrusions and revolutions (`studio/sketch_profile.py`, `sketch_curves.py`): vertices, fillets with their arcs, cubic edges with tangent alignment, the closing vertex, and every refusal of the profile;
* lofts between rectangles, ellipses and circles (`studio/solid_loft.py`): the sections, the number of steps and tiers for the 0.025 mm tolerance, and the mesh of strips and caps, given to the kernel as the Python gives it;
* linear and polar patterns;
* runs of additions, cuts and intersections applied together, done again feature by feature when a run fails so that the error names its feature;
* the mesh, measures and silhouette of the answer;
* horizontal sections, with the straightening of turned faces.

The Python asks the solid kernel for one operation at a time through the `solid` command, and the core asks the same command for the same operations with the same requests. The meshes, volumes, bounds and outlines are therefore the reference's to the bit, and the work stays the kernel's: a plate of 10,716 triangles took 71 ms in the core and 74 ms in Python, with the response's JSON written by the core.

A sketch is checked as Shapely checks it. `Polygon(outline).is_valid` is the closed outline's `is_simple`, decided by the core's port of GEOS's simple-line test (`simple_line.cpp`): on 33,066 generated rings of distinct vertices, touching and crossing ones among them, Shapely's two answers never differed. The area is GEOS's shoelace sum, in its own order. The fillets' trigonometry is the platform library's, as Python's is.

With the reference's rules in force, some models and expressions are declined, as the Python service needed; by the core's own rules, which the programs use, (see [The core's own rules](#the-cores-own-rules)) they are refused. On the model side, these are STEP parts where there is no STEP add-on. Scripted features are rebuilt by the core's script engine (next section), with one geometry budget for all the scripts of a model, as in the Python. On the expression side, they are any expression that Python's own parser might read otherwise than the small grammar here, such as powers, floor division, attributes, tuples, keywords other than `True`, `False` and `None`, comments and non-ASCII text. A call may end with a comma, as Python allows. Python's dictionaries keep their order but the core's JSON objects keep theirs by name, so Studio sends the parameters' order with the model. A circular reference is then reported from the same parameter. `validation/native_core_parity.py` now replays the solid calls of the test suite and 300 generated histories and sections by default (`--solid-cad`). In the measurement for this change, 174 of the generated cases were reproduced as models, 123 as rejections and 3 declined. `tests/test_solid_cad_core.py` compares models, errors, parameter order, expressions and the route.

### Sketch constraints

Sketches with geometric constraints (fixed points, distances, parallel, perpendicular, angle and equal edges) are solved by the core (`solve_sketch` in `native/core/src/solid_cad.cpp`), and this solver is the one Studio uses: the reference's `studio.sketch_constraints.solve_profile` asked the core through the `sketch-solve` command too, and `kerfkite-cam sketch-solve` solves a sketch on its own. It is the reference's Gauss-Newton iteration statement for statement. That covers the relations and their checks, the residuals and Jacobian, the step and the halving of it, the convergence test, the rank for the degrees of freedom, and the messages. The linear algebra is the core's own (`native/core/src/least_squares.hpp`): a singular value decomposition by one-sided Jacobi rotations, giving the least-squares step of least norm and the rank, where the reference has NumPy's LAPACK. On random matrices the step agrees with NumPy's to within rounding times the matrix's condition, so the solved vertices agree to rounding rather than to the bit. Because the reference and the core asked the same solver, a constrained model is still rebuilt identically by the two, and the parity comparison's generated histories include constraints.

`validation/sketch_constraint_check.py` compares the core's solver with the NumPy one on generated sketches of 3 to 12 vertices with up to 16 relations, some contradictory, redundant or degenerate. On 6,000 sketches (seeds 1 to 3), 3,505 were solved by both and 2,327 refused by both. The largest difference in a vertex was 7.3·10⁻⁷ mm, and 4 sketches had a vertex on another point of the kernels' 1 nm grid. Where a system is ill-conditioned the iterations can take different paths, as NumPy's own answer does from one BLAS library to another. Then 8 of the solved sketches had other diagnostics (an iteration more or fewer, or a singular value either side of the rank tolerance). 7 were solved by one solver within its 40 iterations and given up by the other, and 161 of the refusals named another relation as the one that could not be satisfied. The NumPy solver was the reference, `solve_profile(..., backend='python')`, and the solver without the extension.

### Assemblies

Assemblies are solved by the core too (`native/core/src/assembly.cpp`, the port of `studio/assembly.py` and `assembly_constraints.py`), and this is the implementation Studio uses. `/api/assembly/solve` asks the core through `studio.assembly.solve`, and `kerfkite-cam assembly-solve` solves an assembly without Python. The port follows the reference statement for statement:

* the document's checks and messages;
* the part placements and the mate tree, with its cycle test;
* additional mates fitted by Gauss-Newton on the driving joints' free axes, with finite differences, the step limit for rotations and the halving of the step;
* the parts, rebuilt by the history port above and placed by the kernel;
* the shortlist of pairs by their bounds, their interferences and their contacts, all from the kernel.

The matrix products, the inverse (LU decomposition with partial pivoting) and the fitting's least squares (`least_squares.hpp`) are the core's own, where the reference has NumPy's BLAS and LAPACK. The placements therefore agree to rounding rather than to the bit. Studio sends each part's parameter order with the assembly, as it does for a model.

`validation/assembly_check.py` compares the core with the NumPy reference on generated assemblies of 2 to 6 parts. They are joined by mate trees of every kind, sometimes by an additional mate, with faulty documents among them. On 1,200 (seeds 1 and 2), 751 were solved by both, 318 of them to the bit, and 449 were refused by both with the same message. Without additional mates the placements agreed to 10⁻¹² mm. With one, the fit stops once the mates hold to 10⁻⁶ mm, and the placements differed by at most 3.9·10⁻⁶ mm. A last bit of difference in a placement can move a vertex to the neighbouring point of the kernel's 1 nm grid, so an interference's volume may differ by about the overlap's area times 10⁻⁶ mm, and a pair touching within the 10⁻⁶ mm contact distance may be a contact in one and not the other. No pair touched differently in these runs. The NumPy implementation was the reference, `solve(..., backend='python')`, and the fallback without the extension.

### Surfaces

Editable surfaces are tessellated by the core as well (`native/core/src/surface.cpp`, the port of `studio/cad_exchange.py`'s `surface_mesh`), and this is the implementation Studio uses: `/api/solid-cad/surface` and the surface STL export ask the core through `studio.cad_exchange.surface_mesh`, and `kerfkite-cam solid-cad-surface` meshes a surface without Python. The request is `{"surface", "order", "orders"}`, the orders being those of the surface's and each patch's parameters. The core does the reference's work:

* the control nets, kinds, degrees, weights and trim bounds checked with the reference's messages, and the poles' named parameters resolved by the history port above;
* the joins of a sheet resolved in homogeneous coordinates, position and tangent, with their range checks; the resolved patches are the reference's to the bit;
* Bernstein and Cox–de Boor bases on the reference's 25 by 25 grid of each visible window, the rational surface evaluated there, and its area and bounds;
* a drawn outline checked as Shapely checks a polygon, cut to the trim bounds and to each patch, and its pieces cut into the reference's 24 by 24 cells and triangulated.

The evaluation sums the basis products in the core's order, where NumPy's `einsum` has its own, so an untrimmed surface agrees with the reference to rounding (2.7e-15 of its size in the runs below). The outline is cut by the kernel's exact planar arrangement (`region_triangles`, see [the solid kernel](SOLID-KERNEL.md)) on a grid of 1/4096 mm to the UV unit, where the reference clips each cell with Shapely and triangulates it by constrained Delaunay triangulation. The core then flips each cell's diagonals until they are Delaunay, splits a cell whose corners share a circle from its lowest corner, and merges points within 64 grid steps (1.6e-8 in parameters), where the reference meets a grid line at a corner of the outline that the rounded grid passes beside. The trimmed meshes have the same cells, cut at the same points, and the same triangles but for the diagonals of whole cells, which Shapely takes either way as rounding decides; their areas agree to about 2e-4. Outlines whose loops touch one another are declined with the reference's rules in force and refused by the core's own, as are requests that do not reach the core unchanged (a NaN trim bound, say). STEP import and export are Open CASCADE's: the server's STEP add-on, or OCP in the Python.

`validation/surface_mesh_check.py` compares the core with the reference on generated surfaces: patches of every size, kind and degree, weights, named parameters, sheets of two to six patches joined along U or V, trims, outlines with holes, and faulty requests. In three runs of 1,500 (seeds 1 to 3), 3,388 surfaces were meshed alike and 1,375 refused alike, and 38 outlines with touching loops were declined; none differed. `tests/test_cad_exchange_core.py` compares patches, sheets, joins, an outline with a hole, refusals and the route.

## CAD scripts

Studio's CAD script language runs in the native core as well (`native/core/src/scad.cpp`, the port of `studio/scad_language.py` and `studio/scad_geometry.py`). `/api/cad-script` sends the core's answer, the scripted features of a parametric solid are rebuilt by it, and `kerfkite-cam cad-script` previews a script without Python. The request is the route's payload, `{"source", "parameters", "overrides"}`, with the parameters' order beside it as for a model. The port reproduces the following, to the bit:

* **Reading.** The tokens, lines and columns are the reference's. Python's `re` module reads `\s` and `\d` as Unicode classes, so a no-break space separates tokens and an Arabic-Indic or full-width digit is a digit; the core has the same classes. The messages are the reference's, an unreadable character shown as `repr()` shows it. `native/core/src/unicode_tables.hpp` holds the decimal digits and the characters that are not printable. `scripts/build_unicode_tables.py` generates it from the Python that is to be matched; the table in the repository is Python 3.13's (Unicode 15.1). The installed Python 3.12 has Unicode 15.0, so it shows a character added in 15.1 escaped where the table shows it as it is.
* **Evaluation.** Python's int and float are kept apart. `len`, `floor`, `ceil`, `round`, `sign` and `$children` give ints, which stay ints through `+ - *`. Equality, truth and comparisons are Python's, so `true == 1` and `[1] == [1.0]` hold. The functions are CPython's on the platform's maths library. A dot product is summed as `sum()` sums it: compensated for floats, exactly for ints, and in the order CPython changes from one to the other. `norm` is `math.hypot`. Variables are resolved the first time they are read, in the scope where they are assigned, and parameters override assignments at the top level. Modules, functions, `children()`, `$fn`, loops, ranges, comprehensions and conditionals are covered. The evaluation budget is charged unit for unit, so a script that exceeds it fails at the same line and column.
* **Geometry.** Each primitive and operation sends the solid and polygon kernels the requests the Python sends, with the same numbers. The budget, the limits on nodes, elements, coordinates and overlapping work, and every message come with the line, column and operation that failed.

Two decisions rest on arithmetic that the Python leaves to NumPy's linear algebra, whose last bits depend on the platform and its BLAS library even in Python. The first is whether a `multmatrix()` is singular (|det| < 10⁻¹⁴). The second is whether a polyhedron face has an area and is planar and convex within its tolerance. The core takes the determinant from an LU decomposition with partial pivoting, as NumPy does from LAPACK's, and the normal and distances from plain dot products. Only a matrix or face within rounding of the threshold can be judged differently. Whether a polygon path or a polyhedron face crosses itself is Shapely's answer, from the core's port of GEOS's simple-line test (`simple_line.cpp`). A path whose answer depends on rounding inside GEOS is declined with the reference's rules in force, which has not happened in any comparison so far. A source with a lone surrogate (possible in Python text, not in JSON) is also left to the Python.

`validation/native_core_parity.py` compares 1,000 generated scripts by default (`--cad-script`). They cover every primitive and operation with sound and unsound arguments, the language's constructs and limits, the reader's faults, parameters and overrides, and scripts damaged at random. Generated solid histories now include scripted features. In the measurement for this change, 464 of the 967 distinct cases were reproduced as drawings or solids and 503 as rejections, with none declined. 6,000 further scripts from other seeds and 167 hand-picked edge cases also matched. The test suite's calls are replayed too. `tests/test_scad_core.py` compares drawings, solids, the language, parameters and the route.

## Foreign drawings

Posted G-code, HP-GL plotter files and LinuxCNC INI files are read by the native core (`native/core/src/program_import.cpp`, the port of `studio/program_import.py`), and so are DXF drawings, by a reader of its own (below). `/api/program-import` sends the core's answer, and `kerfkite-cam program-import` reads a file without Python. The request is the route's payload, `{"name", "text", "unit"}`. The port reproduces the following, to the bit:

* **The request.** The payload's checks and their order, the choice of reader by the filename's suffix as `pathlib` takes it, the byte-order marks removed from the start, and every message.
* **Reading.** Python's `splitlines()` and `strip()`, the regular expressions of the words, values and comments, `float()` and `round(feed, 5)`, the modal groups and codes, absolute and incremental coordinates and arc centres, arcs given by I/J and by R, and the heights interpolated along a feed move. Arcs are flattened to the same 0.025 mm chord with CPython's maths functions on the platform's library.
* **The drawing.** The limits of 3,000 paths, 100,000 vertices and ±2,000 mm, depths and source heights, layers in their order of appearance, the batching of long runs of contours beyond 100 objects, and the presets and warnings written with Python's `{:g}`.

Program text that is not ASCII is read as the Python reads it: lines end at every boundary `str.splitlines()` knows (U+2028 and NEL among them, and a carriage return before one ends a line of its own), the text is upper-cased as `str.upper()` does (so a long s is an S, and ß is SS), spaces of other scripts are spaces, and digits of other scripts are numbers, as `\s`, `\d` and `float()` take them; an HP-GL instruction is named in its own letters, and an INI's include line is found as `re.I` finds it, with U+0130 and U+0131 matching I. The core reads such text in an ASCII rendering after `str.upper()` (`python_ascii` in `core/src/python_text.hpp`), from Unicode tables generated by `scripts/build_unicode_tables.py`. On Windows, a filename beginning with a UNC or device anchor is declined as well, because `PureWindowsPath` takes its anchor apart in ways the core does not reproduce.

DXF drawings are read by the core's own reader (`native/core/src/dxf.cpp`), written from the DXF format, which is Studio's implementation; the Python reader, built on ezdxf, was the reference and the fallback without the extension. It reads the drawing units, model-space lines, polylines with bulges in their own coordinate systems, 3D polylines, circles, arcs, ellipses and splines, block references with base points, scales, rotations, mirroring, arrays and nesting, planar XCLIP windows, layers with their colours and visibility, and the entities it skips, with every limit and message of the reference. The two differ in how curves become vertices. The reference flattens ezdxf's cubic Bézier approximations of the curves; the core flattens the true curves: arcs and ellipses in equal steps whose sagitta is at most 0.025 mm, and splines by their Bézier pieces, halved until every control point is within 0.025 mm of its chord. The core therefore has about a third fewer vertices, its circles and arcs lie exactly on the curve, and it draws three kinds of spline correctly where the reference does not: rational splines, splines of degree 1 and 2 (millimetres off in the reference), and closed periodic splines, which the reference draws over the whole knot vector instead of the curve's domain, often far outside the drawing. A whole circle, arc or ellipse runs clockwise from its start, and a part of one counter-clockwise, as in the reference. The core also reads the units ezdxf cannot convert (microinches, mils and the US survey units). A spline given only by fit points is interpolated as CAD programs and ezdxf interpolate it, from The NURBS Book (9.2.1, 9.2.2): a cubic B-spline with parameters by chord length and the interior parameters as its knots, through every fit point, with the given end tangents scaled to the total chord length or, without them, no bending at the ends; the control points come from the banded system, solved with partial pivoting. A fit point given twice, which the reference cannot interpolate, is passed through once by the core's own rule.

`validation/dxf_import_check.py` compares the two readers on drawings written by ezdxf. Each must refuse the same drawings with the same message or read them with the same layers, colours, objects and warnings, and every path must agree within 0.05 mm plus 3×10⁻⁴ of its size (the radial error of the reference's cubic pieces); a model-space spline is compared with the curve itself, within 0.03 mm; in a drawing with XCLIP windows, where the readers' chords cross a window's boundary at different points, the runs are compared as sets of points except within twice that bound of a boundary. Three runs of 1,500 drawings (seeds 1 to 3) gave 3,410 drawings read alike, 972 refused alike, and none different; the largest deviation was 0.90 of the bound, and 118 drawings were refused by the reference only, every one because of a closed spline it drew outside the ±2,000 mm range. The drawings now include splines given by fit points, with end tangents and without, in model space (compared with ezdxf's own curve from the fit points) and in blocks: seeds 1 and 2 gave 2,272 drawings read alike within the bound (the largest deviation 0.81 of it), and the 43 with a repeated fit point were declined with the reference's rules. With seed 3 one drawing differs, by an arc of about 2.5 m radius clipped by an XCLIP window: the reference's cubic approximation of the arc is 0.86 mm off the true curve, more than the bound, which the check takes from the clipped drawing's size because a run does not tell its curve's radius; without its fit-point spline the drawing reads the same before and after this change.

For G-code, HP-GL and INI files, `validation/native_core_parity.py` compares 3,000 generated files by default (`--program-import`). They cover sound programs and plots, every refusal, every suffix and unit, long runs that are batched, and payloads the request refuses. In the measurement for this change, 8,659 of 18,493 distinct cases from 20,000 generated files were reproduced as drawings or workspaces and 9,458 as rejections; 376 were declined, all of them DXF drawings (then declined; now read by the core and compared by the check below) or text that is not ASCII. The test suite's calls are replayed too. `tests/test_program_import_core.py` compares drawings, refusals, the fallback and the route.

### PDF pages

PDF pages are read by the native core as well (`native/core/src/pdf_import.cpp`, the port of `studio/pdf_import.py`), without pypdf or Shapely. `/api/pdf-import` sends the core's answer and `kerfkite-cam pdf-import` reads a page without Python; the request is the route's payload, `{"content", "page"}`. The reader is written from the PDF format for the files producers write: the header, a cross-reference table or stream (with PNG predictors, object streams and incremental updates) found from `startxref`, streams whose length is right, and the standard filters, FlateDecode by the core's own inflate (`inflate.cpp`, from RFC 1950 and 1951), LZWDecode, ASCII85Decode, ASCIIHexDecode and RunLengthDecode. From such files it reads what pypdf reads in strict mode: the page tree with its inherited attributes, the boxes, user unit and rotation, and the content streams' operators and operands, numbers as pypdf parses them. The extraction is the reference's statement for statement, with Shapely's predicates answered exactly: orientation by GEOS's test, points on and inside rings by exact tests, simple rings by the simple-line port, and the intersection of convex clipping regions from their corners and the points where their edges cross.

With the reference's rules in force, these are declined: files that depart from that form (pypdf repairs many), encrypted files other than the standard RC4 handlers (which both refuse with the reference's message), pages with inline images (whose end pypdf finds by its own rules), operands pypdf refuses in words of its own, and a point within rounding of a clipping boundary whose corners were computed, where GEOS's rounded intersection could judge it either way. By the core's own rules ([The core's own rules](#the-cores-own-rules)) each is answered: as the PDF format says, by the repairs readers commonly make, or refused as unreadable. `native/tests/selftest.cpp` checks them on pages written by hand (a wrong stream length, looser cross-reference entries, more after `%%EOF`, a page without `/Type` whose resources are not there, a number run into an operator, ASCII85 data without its end marker, an inline image, an unusual string escape, an unusual security handler).

`validation/native_core_parity.py` compares 1,500 generated pages by default (`--pdf-import`): paths, curves, fills and their rules, clipping, forms, graphics states, optional content, text and images, page trees, boxes, units and rotations, every filter, both kinds of cross-reference, and damaged operators, documents and payloads. In a run of 20,000 pages, 12,122 of the 19,333 distinct cases were reproduced as drafts and 6,968 as rejections, and 243 were declined, 175 for a point at a computed clipping boundary and 68 for a number run into a word; none differed. `tests/test_pdf_import_core.py` compares pages, cross-reference streams, refusals, encryption, inflate and the route.

### LightBurn bundles

LightBurn user bundles are read by the native core too (`native/core/src/bundle_import.cpp`, the port of `studio/import_bundle.py`), without zipfile or zlib. `/api/import-bundle` sends the core's answer and `kerfkite-cam bundle-import` lists a bundle or reads one member without Python; the request is the route's payload, `{"content"}` or `{"content", "index"}`. The archive is read as Python 3.13's zipfile reads it: the end record found from the end of the file (behind a comment of up to 64 KiB, and with any data before the archive allowed for), with a ZIP64 end record where its locator points to one, the central directory walked entry by entry, names decoded in code page 437 or, with the UTF-8 flag, in strict UTF-8, ZIP64 extra fields giving sizes and offsets and an Info-ZIP Unicode path field giving the name it stands for, and a member opened through its local header, whose name must match and whose data must end before the next entry (entries that share one header both read it, as zipfile allows with a warning). Stored data is taken as it is and DEFLATE data is inflated by the core's own inflate, which reports the errors zlib reports and keeps what it decoded when the data stops early, as zlib does; the result is cut at the directory's size and checked against its CRC-32. The member's text is UTF-16 after a byte-order mark and UTF-8, with or without a signature, otherwise.

Nothing is declined. Where zipfile stops with something other than its read errors, the core gives its own answer, **Cannot read the bundle or selected text member**: for an entry that needs a ZIP version above 6.3 and for patched or strongly encrypted data (zipfile's NotImplementedError, which the route did not catch), and for a member header placed before the start of the data (zipfile's ValueError from a seek, `negative seek value`). DEFLATE data that inflates past what a member may hold is read as zlib reads it when asked for the 4,000,001 bytes the reference asks for: cut there, with nothing after it looked at.

`validation/native_core_parity.py` compares 3,000 generated requests by default (`--bundle-import`): archives listed and then read member by member, with every suffix, UTF-8 and code page 437 names, unsafe and unprintable names, folders and links, encrypted, patched and newer entries, extra fields, comments, data before and after the archive, member text in UTF-8 and UTF-16, and damaged sizes, checksums, offsets, names and bytes. It also writes ZIP64 end records (with extensible data, the end record's own fields, other locator offsets and disk counts), ZIP64 extra fields (complete and cut short) and Unicode path fields (matching and other names, other versions and checksums, empty, and not UTF-8). Of 10,504 distinct cases from 12,000 requests, 3,037 listings and member texts and 7,068 rejections were reproduced, 373 were cases where the reference raised something other than a refusal and the core refused, and 26 were the core's own answers above; none differed. With a Python before 3.13, which reads ZIP64 end records by other rules, an archive with a ZIP64 locator whose answer differs is counted as the core's own as well. 200,000 damaged DEFLATE streams were inflated as zlib inflates them. `tests/test_import_bundle_core.py` compares listings, members, refusals, damage, what is declined and the route.

## Threads, and a GPU for large reliefs

The relief contact and the stock preview share their work out over the processor's threads. The split is fixed: rasters (relief) or rows of the height map (stock preview) go to the threads in equal runs, each value is written by one thread with the arithmetic of a single thread, and errors are found by a first pass in the order one thread would meet them. The number of threads therefore changes no bit of any result and no error message. A job starts a thread only for enough work (two million contact checks a thread, for the relief), and both release the GIL while they compute. `KERFKITE_THREADS=n` caps the threads; `1` runs everything on the calling thread.

With the compiled extension the relief takes larger maps: image height maps of up to 1024 points a side (256 without it) and jobs of up to 2 × 10⁹ contact checks (10⁷). The editor sends a map larger than 256 as the canvas's RGB bytes (`heightmap_rgb`, base64, with `heightmap_size` as columns and rows, top row first), from which the server computes the luminance the editor would have. `GET /api/session` reports the limit as `relief_map`. STL and artwork reliefs stay at 128: their rasterisers, now in the core (see below), keep the reference's limits. A path still holds at most 100,000 points, so a 1024-point map needs a stepover of about a hundredth of the map's height or more.

### The GPU

A large relief may run on a GPU, or on a GPU and the threads at once. KerfKite uses the OpenCL library that GPU drivers install, loaded when it is first needed: `OpenCL.dll` from the Windows system folder (and from nowhere else), and `libOpenCL.so.1` on Linux. Nothing of OpenCL is compiled in or shipped. macOS runs the contact on the threads. Apple's OpenCL is deprecated and has no double precision on Apple silicon. On an Intel Mac runner, a relief forced onto it (with `KERFKITE_GPU=on`, which takes the processor device) had not finished after 300 seconds, where the threads took 0.7. A stalled run would also have held the lock every relief job takes to ask for the GPU. The few functions used are declared from the public specification in `native/core/src/gpu/opencl.cpp`, behind the interface of `kerfkite/gpu.hpp`. Without the library or a suitable device, everything runs on the threads.

* **Which device.** With `KERFKITE_GPU=auto` (or unset), a GPU with double precision, a discrete one first. An integrated GPU shares the processor's memory and was measured slower than the threads of a large processor, so it is used only where the calibration below measured a gain. A GPU without double precision is never used: on a Raspberry Pi, whose GPU has no OpenCL driver with double precision that we know of, the contact runs on its four cores. `KERFKITE_GPU=on` gives every job to any device with double precision, a discrete GPU first, for tests and measurements; `off` uses none. The device is chosen once per process.
* **Calibration at start.** Studio measures the computer each time it starts, because the answer depends on the processor, the GPU, its driver and what else is running. Two seconds after it opens, a background thread (`studio.relief.calibrate_in_background`, `kerfkite::relief_calibrate`) runs one contact job sized to take about 40 ms on all the threads. It then runs the job on the GPU alone, which sets the GPU up, and a job of a few rasters for the GPU's fixed cost per run. Last it runs both at once, the GPU beside all the threads and beside one fewer, since on a processor with few cores the thread that drives the GPU may need a core to itself. Each shared run's split is corrected once from what each side took. Every run's depths are compared with the threads' whole answer bit for bit, so a GPU that differs anywhere is turned off before it is used for real. From then on a large job goes to the threads, the GPU, or both, whichever the measurements favour. A way is taken only where it is expected to save a twentieth of the time. Without a usable GPU only the threads are measured, in about a tenth of a second. `kerfkite-cam calibrate` prints the report, and `studio.relief.calibration()` returns the last one.
* **Sharing a job.** The GPU takes the first rasters, as many as make up its share of the checks, and the threads take the rest. Each raster is computed whole by one side, so the depths are the threads' bits whatever the share. The share is the one at which both are expected to finish together, given the measured speed of a thread and the GPU's speed and fixed cost. 128 of the GPU's contacts are checked as before. If the GPU fails or differs, the threads compute its rasters afterwards and the GPU is turned off. Every job refines the speeds.
* **The same bits.** The kernel is the contact arithmetic of `segment_contact` in `native/core/src/relief.cpp`, written out statement for statement in OpenCL C: double precision, no fused multiply-add, and maximum and minimum written to choose as `std::max` and `std::min` do. OpenCL requires double-precision division and square root to be correctly rounded, as they are on the processor. Each result is still checked: 128 of its contacts, the four corners among them, are computed again on the processor and compared bit for bit. On any difference the result is discarded, the job runs on the threads, and the GPU is turned off for the rest of the process.
* **Before a calibration.** `kerfkite-cam` does not calibrate, and Studio's first jobs may come before its calibration has finished. Then only a discrete GPU is used, and only alone. A job of fewer than 2 × 10⁸ checks stays on the threads, because its fixed costs on a GPU (buffers, transfers, launches) would take the gain. Setting a GPU up the first time in a process took 0.1 to 0.3 s. Large jobs therefore run on the threads until they have spent that long there between them, or until one job alone is expected to. Then the GPU is set up, and each later large job goes to whichever of the two has been measured faster.
* **No driver resets.** Work goes to the device in slices that start at 64 contacts and grow to about 50 ms each, so no launch comes near the two seconds after which Windows resets a display driver, however slow the device is.
* **What it reports.** The editor says **C++ accelerated relief on the GPU** when a GPU computed the contact, and **on the GPU and processor together** when they shared it. The result's `device` is `gpu`, `gpu+cpu`, `cpu` or `python`; it is kept out of `surface`, which is saved with the design and is the same on every computer. `studio.relief.gpu_status()` names the device in use, or says why there is none.

Measured with `validation/benchmark_relief.py` on a laptop with an Intel Core Ultra 9 275HX (24 threads) and an NVIDIA GeForce RTX 5090 Laptop GPU (OpenCL 3.0, driver 617.71): a whole relief prepared from a synthetic RGB image of a 100 × 100 mm map with a ball cutter, from the image's base64 text to the paths and depths as Python objects, best of five (of six on one thread). The depths had the same digest in every way, under MSVC on Windows and on the GPU as under GCC on Linux. The 8 and 4 thread columns are the same processor with `KERFKITE_THREADS` capping it, standing for smaller processors.

Run after run on 4 threads, the calibration chose the GPU alone once and the GPU with 4 threads once: there the two differ by less than the margin of a twentieth, which is one reason the measurement is repeated at every start. The installed-wheel check runs a relief from a 400-point RGB map against a recorded digest, on the threads, on one thread and, where there is a GPU, forced onto it.

The stock preview stays on the threads. Its arithmetic is now the four operations, square roots and rounding to whole numbers, with CPython's `hypot` built from them and exact scaling by powers of two, and one `tan` for a job, so a GPU version could give the same bits; whether it would be faster has not been measured. The solid and polygon kernels make their decisions in exact integer arithmetic and do not use a GPU either.

## G-code and rotary output

Studio's G-code and rotary output come from the native core (`native/core/src/cam.cpp`, `rotary.cpp` and the files beside them). While the reference existed, the core was compiled into its extension and called through `core_cam` (`studio/_core_native.cpp`): `studio.cam.generate`, `studio.rotary.generate_rotary` and `studio.rotary.wrap_job` handed the request over and returned the core's job, and the Python modules behind them were the reference the core was compared with and the fallback. The interface was:

* **What crosses to the core.** A request goes to the core only when JSON would carry it unchanged: `None`, booleans, integers within 64 bits, finite floats, text, and lists and dicts with text keys, each of exactly that type. A tuple, a float subclass, a non-finite number or a key that is not text stayed with the Python reference, which gave its own answer or message.
* **What the core declines.** The few cases it does not reproduce exactly (a contour whose self-crossing test turns on rounding inside GEOS, among them) raised `NotImplementedError` inside the call, and the Python reference answered them; the programs answer them by the core's own rules.
* **The job is Studio's job.** The core gives every member the Python job has: the program lines, the preview segments with the reference's number types (the integer 0 of a laser move's height and of a beam-off gap), the cut length and time, bounds and warnings, the paths and depths cut, and for drilling the holes and the drill, or for an ordered job the number of operations. The job is built as Python objects directly from the C++ one, not written as text and read back, and the rows of the preview share the float objects of the points they have in common.
* **Previews as text.** The preview routes (`/api/generate` in both servers and `/api/rotary`) send the core's own JSON text of the job (`studio.cam.job_json`, `studio.rotary.rotary_json`), with names in byte order and numbers written as Python writes them, as Flask's `jsonify` would give them. For a large job that is most of the time of the request.

In the Python service, `KERFKITE_GCODE_BACKEND=python` made `auto` use the Python CAM, and so did `KERFKITE_POLYGON_BACKEND=shapely`; the programs have no such switches.

**The output is identical, not merely close.** The core writes fixed-point text with exact integer arithmetic, rounding half to even on the exact binary value as Python does; squares use the same `pow` call that Python's `**` makes; `math.dist`, `sum()` and `math.hypot` are reproduced step for step as CPython 3.12 computes them (`kerfkite/py_math.hpp`); and the rotary post's `asinh` is the C library's, which is what CPython 3.11 and later call. `validation/native_core_parity.py` compares the core with the Python reference on every generator and rotary call the test suite makes, on 20,000 generated projects, 6,000 ramp, helix and tab jobs, 5,000 helical pockets, 4,000 V-carves, and 3,000 rotary jobs with 1,500 given programs, on Linux, macOS, Windows and ARM in CI: every case is reproduced or declined.

`tests/test_native_gcode.py` compares the two for router, relief, laser, perforated and bridged jobs, in list and packed forms, with number types and every member of the job; drilling, ordered, ramp, pocket and knife jobs; what may cross to the core and what stays with the reference; the environment switches; the JSON text; 96 rotary option combinations, the rotary limits and given programs. `validation/benchmark_gcode.py` times the Python reference against the core and fails if their program hashes differ.

The extension kept two small pieces of its own here (`studio/_gcode_native.cpp`): unpacking packed preview rows at the JSON boundary, and the core's fixed-point text and `round()`, which its tests compared with Python's formatting; `validation/check_pinned_results.py` compares the core's text with Python's `format()` now. The core generates the whole job.

## The workstation server

`kerfkite-studio` (`native/server/`) is the local workstation server without Python: the editor in `studio/static` served as it is, with every route of `studio/server.py` and of the design routes it registers, over the core. It is KerfKite's own code and needs nothing but the C++ standard library and the operating system: its own HTTP/1.1 server (one request a connection, `Content-Length` or chunked bodies, 64 KiB of header fields, a 30 s receive timeout), USB serial ports through termios on Linux and macOS and the Win32 communications API on Windows (listed as pyserial lists them), and random tokens from the operating system (`BCryptGenRandom`, `getentropy`, `getrandom`). It builds with the core and runs in simulator mode unless started with `--enable-hardware`:

    kerfkite-studio [--port 8765] [--enable-hardware] [--monitor] [--monitor-port 8766] [--monitor-plaintext] [--step PROGRAM] [--static DIR]

It binds the loopback interface, prints its address and `KERFKITE_READY` (the line the desktop launcher waits for), and keeps the Python server's guards: the `Host` check against DNS rebinding, the session token on every `POST`, the controller lock held through each machine-control request, and the body limits (8 MiB, the stock preview's own binary and JSON limits). The controller transports are ported from `controller.py`, `marlin.py` and `device.py` statement for statement: acknowledgement pacing, holds, timeouts, the simulator and its probed surface, Marlin's line numbers, checksums and resends, and the read-only machine readback; probe levelling, the rotary checks, the phone's armed start and its confirmation at the workstation are those of `server.py` and `phone_jobs.py`. Python dictionaries keep the order their keys were written in, and named parameters are resolved in that order, which decides which of two faults a sketch or a model reports; the core's JSON keeps names in byte order, so the server reads the order from the request's text (`key_order.cpp`) and passes it with the request, as the extension does.

The phone pendant's HTTPS comes from a relay, `kerfkite-pendant-tls` (`packaging/pendant-tls`), because TLS is not written here: it is Go's standard library (`crypto/tls`, `crypto/x509`, `crypto/ecdsa`) and nothing else, and CMake builds it beside the server when Go is installed. For each pairing the server binds the monitor app to the loopback interface and starts the relay, which makes a certificate for the pairing as `studio/monitor_tls.py` did (ECDSA P-256, self-signed, valid for 30 days, for the machine's name and addresses, not a certificate authority), keeps its private key in memory, listens for the phone with TLS 1.2 or later and passes each connection on. It announces the certificate's SHA-256 fingerprint, which goes into the pairing link (`&fp=`) for Pocket to pin, and it ends when the pairing ends or the server stops, because the server holds its standard input. `--monitor-cert` and `--monitor-key` serve an operator's certificate instead, and `--monitor-plaintext` keeps HTTP for Pocket 0.4.1 and earlier. Without the relay program, pairing is HTTP and reports `can_encrypt` false, as the Python service did without its TLS libraries. `validation/pendant_tls_pin_check.py --server <kerfkite-studio>` makes requests with Pocket's own pinning class (`PinnedTls`) to three servers on the loopback interface: the paired certificate is accepted, a wrong bearer token is refused by Studio, and another pairing's certificate, another receiver and a plaintext listener are rejected. `go test` in `packaging/pendant-tls` checks the certificate, the relay and its refusals.

STEP exchange runs in a program of its own, `kerfkite-step` (`native/step/`), the only part of KerfKite that uses Open CASCADE Technology, an exact B-rep modeller whose reader, tessellation, Booleans and writer STEP needs. Open CASCADE is LGPL 2.1 with the OCCT exception, so it is kept apart: the add-on links Open CASCADE's shared libraries, which stay separate files that can be replaced with another build of the same release, and the rest of KerfKite links nothing of it. CMake builds the add-on when it finds Open CASCADE 7.6 or later (`-DOpenCASCADE_DIR=<prefix>/lib/cmake/opencascade`; the releases are to use 7.9.3, the release the Python reference's OCP carries), and the server uses it from beside itself or from `--step PROGRAM`. The server does the reference's own work in KerfKite's code: it decodes and checks the document (its size, its `ISO-10303-21;` header and end, the entity budget) and the core turns a part into the steps of `cad_exchange._part_shape` (`step-part`: boxes, spheres, cylinders and cones, the exact rational quarter patches of a loft, a sketch's exact edges (lines, cubic Béziers and fillet arcs through their midpoints) extruded or revolved, embedded STEP solids, turns, moves, pattern copies and Booleans, in feature order) and a surface into the faces of `_surface_shape` (`step-faces`: poles, weights, the open uniform knots of a B-spline, and each piece's window or UV outline). For each request the server starts the add-on, sends one JSON request on its standard input and reads one answer, so a fault inside Open CASCADE refuses that request and the server goes on; one request runs at a time, as the reference held a lock. Solid features of kind step reach the add-on the same way, through a hook the server gives the core (`set_step_mesher`), and are welded into a solid by the solid kernel where the reference merged them with manifold3d. Without the add-on the STEP routes answer that STEP needs Open CASCADE, and a solid feature of kind step names its feature with that message. Where the reference failed with an OCP exception it did not catch (a 500), the add-on refuses with a message.

`validation/step_exchange_parity.py --server <kerfkite-studio>` compares STEP with the reference's OCP: generated parts and surfaces exported, the documents written again from their content, imported, turned into STL, damaged ten ways, and used as solid features. Two documents are compared by reading both with the reference's Open CASCADE: the same faces, solids and closed-solid flag, the exact volume and area within 10⁻⁹ of the shape's size, and the extent of a fine tessellation (Open CASCADE's optimal bounds of a trimmed spline face depend on where its outline starts: on one surface they put the reference's face 3.4 mm beyond its true extent and the add-on's at it). With the same release on both sides, imports must give the same mesh, which needs the tessellation's chord tolerance worked out as NumPy works it out: the diagonal's squares summed with fused multiply-adds. With Open CASCADE 7.9.3 on both sides, on Linux x86-64, three seeds of 200 parts and 200 surfaces gave 1,996 cases and none differed: 699 documents described the same shapes, 467 of them identical in text but for the time of writing and the product's serial number (the rest trim faces with outlines that start elsewhere); 131 imports gave the same mesh and STL; 882 requests were refused alike; 12 were declined by the core (dimension expressions it does not read as Python does, and outlines whose loops touch); and 9 garbled documents crashed the reference's process, where the server refused the request and went on. With Ubuntu 24.04's Open CASCADE 7.6.3 in the add-on, the documents it wrote described the same shapes only to 10⁻⁶ (its Booleans and trims round otherwise), 7.6 read some documents that 7.9 writes otherwise (a polar pattern of fused spheres came back with a quarter of its volume), and its meshes differ: 113 release differences in the same cases, which is why the releases are to ship 7.9.3. The CI workflow builds the add-on against Ubuntu's package on Linux and runs the comparison there with that allowance. The desktop packages carry `kerfkite-studio` and the launcher starts it ([Installer builds](INSTALLER-BUILDS.md)); from Studio 0.7 no package carries the Python service.

Answers that came from Shapely in the Python service come from the core's kernels here, so they agree in what they describe rather than in their vertices: `/api/geometry` (unions, differences, intersections and round offsets of artwork, on the polygon kernel, whose arcs are circumscribed where GEOS's are inscribed) and `/api/extrude` (the prism of the artwork on the solid kernel, a closed mesh of the same volume). Where the Python route failed with an unhandled exception (a path that is a number, in `/api/extrude`), the server refuses the request with a message.

`validation/server_route_parity.py --server <kerfkite-studio>` sends the same requests to the Flask app and to the server and compares the answers: the status, and the JSON value for value or the STL byte for byte, with the two routes above compared by their region and their volume. Its cases are the guards, every `GET` route and static file, every `POST` route with malformed bodies, valid requests to each design route with mutations one or two levels deep (a member removed, or replaced by a value of another type or out of range), the binary stock preview, and a script of machine-control steps run on both simulators in turn: connection, runs, jogs, homing, zero, head modes, the armed preview, probing, collecting, a levelled program and run, and a Marlin connection. On Linux x86-64 (GCC 13, Python 3.13), five seeds of 30 mutations a request gave 8,115 cases: none differed (`can_encrypt` is reported apart); 465 were STEP requests, which the server declines, and on 92 the Python route had failed with an exception. `validation/simulate_solid_workspace.py --url http://127.0.0.1:8765/` runs the browser lessons against a running server, and `--step` adds the lessons that need STEP: against `kerfkite-studio` with its Open CASCADE 7.9.3 add-on all 67 checks passed, without the lessons that need the Python controller object. `native/tests/server_selftest.cpp`, which CTest runs, checks the guards, the machine routes on the simulator and on a scripted Grbl link (a laser-mode controller refusing a router job before anything is sent), probe levelling, the phone's armed start with and without the workstation's confirmation, pairing over the relay (HTTPS, a new certificate each time, the relay ending with the pairing), the design routes' own code and the HTTP server on the loopback interface.

## The hosted editor

`kerfkite-web` (`native/server/web_main.cpp`, `web_app.cpp`, `web_store.cpp`, `web_transfer.cpp`) is the hosted HTTPS editor and upload-only machine inbox without Python: `studio/web_server.py`, `web_store.py` and `web_transfer.py` in C++, with the editor in `studio/static`, the design routes, the machine profiles and job generation shared with the workstation server (`add_design_routes` and `add_cam_routes` join either server's route table), and no controller. Its commands are the Python's, with the same messages:

    kerfkite-web [--data-dir web-data] create-user|reset-password USERNAME [--generate-password]
    kerfkite-web [--data-dir web-data] issue-token|revoke-tokens USERNAME
    kerfkite-web certificate --cert FILE --key FILE --hosts HOST [HOST ...]
    kerfkite-web [--data-dir web-data] destination NAME --url URL [--ca-file FILE] [--allow-http]
    kerfkite-web [--data-dir web-data] serve --public-url URL --cert FILE --key FILE [--host 0.0.0.0] [--port 8443] [--allow-file-upload]

Each request is checked as `create_app` checked it: the `Host` must be the public URL's, a page or route needs a live session (a `__Host-` cookie, eight hours, thirty minutes idle), every request that changes something needs the session's token and the public origin, `/api/receive` takes an upload token instead (from a page opened as a file only with `--allow-file-upload`), bodies are limited to 10 MiB, and every answer carries the same security headers (`no-store`, `nosniff`, HSTS, the content security policy). Logins are limited to ten failures in fifteen minutes for an address and for an account, the attempt reserved before the password is checked. Uploads are a simple file name with one of Studio's extensions and up to 8 MiB of UTF-8 text, the same checksum checks, 200 files and 64 MiB an account. A file is sent to a receiver only if the operator configured it, with no proxy, no redirect followed, TLS 1.2 or later and the receiver's own certificate authority if it has one, and only a receiver's confirmation of the checksum and size counts as sent. Where Flask answered with its HTML error page, `kerfkite-web` answers `{"error": ...}` with the same status; a login form that has expired gets a page that says so, with a link to log in again.

TLS is not written here: `serve` starts KerfKite's TLS relay (`kerfkite-pendant-tls`, the program the phone pendant uses, Go's standard library), which listens on the public address with the operator's certificate and TLS 1.2 or later and passes each connection to `kerfkite-web` on the loopback interface, with a PROXY protocol line (version 1) that names the client for the login limits. The relay makes the certificate for `certificate` too (ECDSA P-256, self-signed, 90 days, for the hosts given, never over a file that is there) and makes the one HTTPS request of a send, reading the receiver's token on its standard input rather than its command line. `serve --behind-proxy` listens on 127.0.0.1 for a TLS terminator of the operator's own instead (nginx, HAProxy), which must send the same PROXY line; forwarded HTTP headers are still not trusted.

The store is a folder of the operator's (`--data-dir`, made private to the account that runs the server): `web-store.json` holds the accounts, sessions, failed logins, upload tokens and file records, and `files/` each stored file's bytes, both written whole, flushed and renamed into place under a lock that other `kerfkite-web` processes take too (creating a user while the server runs, say). Sessions and upload tokens are kept as their SHA-256 digests. Passwords are PBKDF2-HMAC-SHA256 hashes in werkzeug's format (600,000 iterations, a 32-character salt); the hashes come from the system: CNG (`bcrypt.dll`) on Windows, CommonCrypto on macOS and OpenSSL's libcrypto elsewhere, opened when first needed. A folder that holds the Python service's `web.sqlite3` and no store yet is moved over when the server or a command first opens it, by KerfKite's own reader of SQLite's file format (`sqlite_reader.cpp`; nothing of SQLite is used): the accounts with their password hashes, the upload tokens and the files keep working, and everyone logs in again; the database is renamed `web.sqlite3.migrated`, and one with an unfinished change in its journal is refused. The Python's hashes are scrypt, which only libcrypto has: on Linux they are checked as they are and replaced by a PBKDF2 hash at the account's next login; on Windows and macOS such an account's password must be set again with `reset-password`.

`validation/web_route_parity.py --server <kerfkite-web>` starts both from the same Python-made store (an scrypt account, a PBKDF2 account, an upload token and stored files), the Flask app in process and `kerfkite-web` on a moved copy, and sends both the same session's requests: the pages and routes before logging in, the login form and logins that fail and succeed, the session, the editor's files, writes without the token or from another origin, saving, listing, downloading and deleting files (the moved files keep their identifiers and bytes), methods each route does not have, generation and a design route, the inbox with the Python-made token, generated upload bodies to the account, the inbox and the receivers, logging out and ten failed logins from one address. The status, JSON answers value for value, redirects, cookies (names and attributes), the security and CORS headers, the login page and the plain-text answers must agree; `--tls` runs it through the relay over HTTPS. On Linux x86-64 two seeds of 1,200 bodies (2,442 cases) and one of 400 over TLS (467) gave no difference, 27 of each run being Flask's HTML error pages. `native/tests/web_selftest.cpp`, which CTest runs, checks the system's hashes against werkzeug's and its RS256 signature checks against signatures made for the test, the SQLite reader and the move of a synthetic Python store (`native/tests/data/web-store`, from `validation/web_store_fixture.py`), the store's limits, tokens and files, the upload and receiver checks, every route through the request checks, the PROXY line of the HTTP server and, with the relay, a file sent to a receiver and the receiver's answers that do not confirm it.

## The assistant server

`kerfkite-mcp` (`native/server/mcp_main.cpp`, with `mcp.cpp`, `mcp_tools.cpp`, `workshop.cpp`, `browser.cpp` and `remote_tools.cpp`) is Studio's assistant server, `studio/mcp_server.py` and the modules it registers, without Python. The Model Context Protocol (versions 2024-11-05 to 2025-11-25) is KerfKite's own code, written from the specification: JSON-RPC 2.0 over standard input and output, a message a line, each tool's arguments checked against the schema the Python server declared, its defaults filled in, before the tool runs. The tools' names, descriptions, schemas and annotations are those FastMCP published (`mcp_declarations.inc`), and clients list them in the Python server's order. Its options are the Python's, with the programs it uses:

    kerfkite-mcp [--output-dir DIR] [--transport stdio|http] [--port PORT] [--show-workshop] [--static DIR] [--templates FILE] [--step PROGRAM] [--tls-relay PROGRAM] [--chromium PROGRAM]

With `--transport http` the server is a hosted workshop for one operator, as the Python server is with FastMCP's stateless HTTP transport (`native/server/mcp_http.cpp`, `oauth.cpp`, `ip_address.cpp`, `os_crypto.cpp`). It listens on the loopback interface (`--port`, 8775 by default) behind the operator's HTTPS reverse proxy, and names its endpoint on standard error. The settings are the reference's (`KERFKITE_MCP_PUBLIC_ORIGIN`, `KERFKITE_MCP_ISSUER`, `KERFKITE_MCP_SUBJECT` and `KERFKITE_MCP_JWKS_URL`), read in its order and refused in its words. What FastMCP, the MCP SDK, Starlette and uvicorn do with a request is reproduced, read from their source as a test oracle: the Host must be the public origin's or a loopback name (421) and an Origin the public origin, the request's own, or a loopback one for a loopback host (403); the protected-resource metadata is served at `/.well-known/oauth-protected-resource/mcp` with its CORS; `/mcp` takes a POST of one JSON-RPC message, checks its media types and protocol version as the SDK does, and answers a request with one server-sent event and a notification or a response with 202; DELETE is refused, there being no sessions; other methods, paths and a final `/` get Starlette's answers; a request without a token, or with one that is not accepted, gets FastMCP's 401 and challenge. A bearer token is accepted as FastMCP's JWTVerifier and joserfc accept it: an RS256 JSON Web Token within joserfc's sizes, its header members of the types joserfc requires, signed by a key of the issuer's key set (by its `kid`, or the only key when the token names none), from the issuer, for the audience `<origin>/mcp` and the subject, with the scope `kerfkite:workshop`, unexpired and already valid. The signature is checked by the system's cryptography (CNG on Windows, the Security framework on macOS, libcrypto on Linux, loaded when first needed); none is written here. The key set is fetched by the TLS relay as FastMCP fetches it: every address of its host must be public by Python 3.13's `ipaddress` tables (an IPv4 address inside an IPv6 one included), each address is tried in turn with the host's name for SNI and Host, ten seconds each within thirty in all, and the answer must be a 200 of at most 64 KiB. A key whose members joserfc, or whose numbers cryptography, would refuse (a point off its curve, an exponent out of range) is passed over when the set is read, as FastMCP passes it over, and a token whose key is not an RSA key is refused. Keys are kept for an hour, and a token that names a key not kept refreshes the set at most once every thirty seconds. The capabilities are announced as FastMCP announces them on each transport: the lists of prompts and resources change only over HTTP.

The template collection, artwork and template-library files, job previews and G-code exports, Studio's design calculations and the workshop's files are computed in the process by the core, and written only in the output folder, under names the server makes. The workshop is the editor in a browser of its own, the program given by `--chromium` or `KERFKITE_MCP_CHROMIUM`, or else an installed Chrome, Chromium or Microsoft Edge, driven over the DevTools protocol on a pipe (`--remote-debugging-pipe`) rather than through Playwright. Each page and its workers are set up before they run: requests are limited to the editor's own origin, the window, screen, focus and media are emulated as Playwright emulates them, and service workers are kept out. The actions are Playwright 1.65's as Studio's Python used them, read from its source as a test oracle: the states each action waits for (visible, enabled, editable, stable over two animation frames, not inert), the retries and their scrolling, the point clicked, typing and the key table, the waits for a navigation, and the conversion of what a page's script returns. Chromium's sandbox stays on, so the server runs as an account other than root. The editor's storage is saved in Playwright's storage-state format, under a lock the Python server also takes, so either server opens what the other saved.

The pendant tools (`studio/mcp_pendant.py`) and the hosted-editor tools (`studio/mcp_files.py`) are offered when the operator configures them, with the same environment variables (`KERFKITE_PENDANT_URL` with `_TOKEN` or `_TOKEN_FILE`, and `_CA_FILE`; `KERFKITE_FILES_URL`, `_USERNAME`, `_PASSWORD` or `_PASSWORD_FILE`, and `_CA_FILE`). A wrong configuration stops the server when it starts, with the reference's message. A jog, homing, setting zero, starting or resuming a job, and deleting or sending a hosted file still wait for the operator's confirmation through the client (MCP elicitation). TLS is not written here: each request is made by KerfKite's TLS relay (`kerfkite-pendant-tls -fetch`, Go's standard library), which reads the token or password on its standard input, uses no proxy, follows no redirect, needs TLS 1.2 or later, and trusts the operator's certificate authority when one is set. What the reference's http.client, json and http.cookies made of an answer is reproduced: http.client's limits on the head (more than 99 header lines, or a line of more than 65,536 bytes, fail); a body cut short of its Content-Length is what arrived; an IPv6 address given without a port is read as http.client reads it (its last group taken for the port, or the connection refused as an invalid URL); header fields are read from the head's lines as the email parser read them (each byte a character, folded lines kept); Set-Cookie headers are parsed as SimpleCookie parses them (its pattern, quoting, attributes and errors); `int()` reads other scripts' decimal digits and Unicode white space as CPython does; and Python's own words are kept where they reach a result (`UUID()`, `int()`, `str()` and `repr()` of JSON values, and CPython's message for a file that is not UTF-8).

The server's own rules, where it differs from the reference:

- An answer whose head holds a control character other than a tab is refused as a failed connection: Go's HTTP client refuses it, where http.client read it.
- Integers past 64 bits are read as the nearest double, where Python kept every digit; a 34-digit number given as a session token or a receipt's identifier is therefore refused.
- Answers are read as JSON in UTF-8, where json.loads also read NaN and Infinity, and UTF-16 and UTF-32 by their first bytes.
- A CA file is read as Go reads it, as PEM certificates with a block that does not parse passed over; OpenSSL refused such a file, and also read certificate revocation lists from it.
- A configured address that is not UTF-8 is refused when the server starts.
- A start that fails prints its reason as a usage error (exit status 2), where Python ended with a traceback.
- The members of a JSON answer are written in byte order, where FastMCP kept the order they were made in.
- Messages, and over HTTP a token's header and claims and the key set, are read by the server's own JSON reader, from UTF-8 or, over HTTP, from UTF-16 and UTF-32 by their first bytes as json.loads read them. It refuses NaN and Infinity, which pydantic and json.loads read; a surrogate without its pair, which json.loads read; and arrays and objects nested more than 200 deep, which json.loads read up to Python's recursion limit (a token nested past it failed with a 500, and gets a 401 here). Integers past 64 bits are read as the nearest double.
- A resource asked for by an address that is not one of the server's is named in the error with its scheme in lower case and the rest as given, where pydantic's AnyUrl wrote it in the URL Standard's form.

Over HTTP, its own rules are:

- The public origin, the issuer and the key set's address are taken only as plainly as pydantic's AnyHttpUrl writes them: in ASCII, with `://`, a host of letters, digits, `-` and `_` without international (`xn--`) labels or an IPv4 address in dotted decimal, and a path with nothing the URL parser would encode or resolve (`%`, `"`, `<`, `>`, `` ` ``, braces, dot segments). Other forms, which AnyHttpUrl normalised, are refused when the server starts.
- `--port` takes ASCII digits for a port from 0 to 65535, where argparse took what `int()` reads and the bind failed past 65535.
- A private key (one with `d`) in the key set is passed over, where joserfc used its public part.
- The text after "Parse error:" and "Validation error:" is the server's own.
- A confirmation asked over HTTP fails at once, where the reference waited for an answer that, without sessions, could not reach it.
- The event stream has no keep-alive comments, and the connection closes after each answer.
- A request's head may have up to 64 KiB and its body 64 MiB, and HTTP the server's reader cannot read is refused in its own way, where uvicorn's parser set its own limits and reasons.
- FastMCP's settings (`FASTMCP_*`, such as `FASTMCP_SSRF_TRUST_PROXY`) are not read.
- The key set is fetched by the relay without a proxy, trusting the system's certificate authorities (FastMCP trusted certifi's), with the relay's request headers; an answer Go's HTTP client refuses fails the fetch, where httpx's refusals were its own.
- `--transport http` needs the TLS relay beside the server or given by `--tls-relay`.

`validation/mcp_parity.py --server <kerfkite-mcp>` compares the declarations, the order of the tools, the resources and generated calls to the tools that need no browser with the Python server's, in process: 424 cases, none different (44 refused by both schemas in their own words, one geometry the same by what it describes). `validation/mcp_workshop_parity.py --server <kerfkite-mcp> --chromium <chrome>` runs a scripted session and a random walk over the editor's controls on both workshops with the same Chromium, then has each server open the storage the other saved: seeds 1, 2, 3 and 6 gave 772 cases and none differed (an error of a browser driver needs only to be an error on both). `validation/mcp_remote_parity.py --server <kerfkite-mcp> --web <kerfkite-web>` starts both servers with 450 environments, points both at a monitor stand-in over HTTP and HTTPS and at a hosted-editor stand-in over HTTPS, and runs a session against two `kerfkite-web` servers made from one account store, with a receiver: listing, uploading, downloading, sending and deleting. The stand-ins answer as KerfKite's servers do and as faulty ones might: redirects and other statuses, oversized, cut-short and non-JSON bodies, too many headers, folded fields and 400 generated Set-Cookie headers a seed; the operator accepts, declines or cancels each confirmation. Results, error texts, the requests each stand-in received and the confirmations asked must agree. On Linux x86-64 three seeds gave 4,656 cases: none differed, and 18 differed by the rules above. `validation/mcp_http_parity.py --server <kerfkite-mcp>` compares both transports with the Python server's, in network and mount namespaces of its own with no proxy: the loopback interface carries public addresses for stand-ins of the issuer's key set, served over HTTPS with a certificate authority made for the run, and host names that must be refused. It sends both HTTP servers the same requests (the guard, the routes and their methods, the metadata and its CORS, generated tokens with every kind of fault, media types, protocol versions, every method with good and bad parameters, and calls to the tools that need no browser); starts a pair of servers for each of 39 key sets (several keys, none, keys without a `kid`, unusable, unsupported and private keys, sets that are not JSON, statuses and oversized answers) and sends tokens that find and miss their keys, with the refresh limit and the addresses a key set may not be fetched from; starts both with a few hundred environments, which both must refuse in the same words or start alike; and sends both stdio servers the same lines. Statuses, the headers that carry meaning, bodies, event data and the requests each stand-in received must agree, geometries by what they describe. On Linux x86-64 three seeds gave 5,584 cases: none differed (one geometry the same by what it describes), and 219 differed by the rules above (150 by the plain form of URLs, 57 by the JSON reader, 9 by private keys and 3 by the size of a request's head).

## How the core was ported

The core was built up beside the Python, part by part, and each part was compared with the reference before Studio used it; this section records the order and the measurements. `native/` began as a C++17 library and the `kerfkite-cam` command-line tool, which wrote G-code from a project file with no Python installed. It came to reproduce router line jobs, laser line jobs (leads, power ramps, perforation, holding bridges and raster powers), drilling, drag-knife paths, inside and outside offsets, pockets, hatch fills, V-carving, ramp entries, helical entries into pockets, holding tabs, ordered multi-operation jobs and controller post-processing: every operation of a job. What it could not reproduce exactly (a number written in non-ASCII digits, a contour whose self-crossing test turns on rounding inside GEOS) was declined, never approximated, and is now answered by the core's own rules. It contains no third-party code and its build downloads nothing. `native/README.md` lists what is ported and how to build it.

Probe levelling (`native/core/src/leveling.cpp`) was the first part of the application written only in the core: it never had a Python version. The extension compiled that file and exposed it as `core_call`, which `studio/leveling.py` wrapped; the extension was therefore built as C++17 and compiled the core's JSON reader and writer with it. See [Probe levelling](PROBE-LEVELING.md).

Circuit board import (`gerber.cpp`, `excellon.cpp`, `pcb.cpp`) was written the same way, compiled into the extension and wrapped by `studio/pcb_import.py`. So were isolation toolpaths (`isolation.cpp`), for which the extension also compiled the polygon kernel (`polygon/`). See [Circuit boards](PCB.md).

Offsets, pockets, hatch fills and V-carving are computed by the core's own polygon kernel (`native/core/src/polygon/`, `native/core/src/operations.cpp`, `native/core/src/vcarve.cpp`; see [The polygon kernel](POLYGON-KERNEL.md)). This was the third part with a single implementation: the extension compiled the kernel and the operations, and `studio/operations.py` called them through `core_call` after checking the job's settings in Python, so Studio and `kerfkite-cam` cut the same paths by construction. GEOS, which the core built for these operations at first, has been removed from the native build with its options.

Without the extension (the portable wheel) the Python ran the same operations on Shapely, as it did before the kernel. That fallback cut the same regions, but its vertices are not the kernel's: arcs are approximated from inside the true arc and not from outside, rings start elsewhere, pockets have many more vertices, a contour that closes only to within the tolerance is usually refused, and a V-carve is written as one path for each piece of the diagram, in no particular order. `KERFKITE_POLYGON_BACKEND=shapely` selected the fallback where the extension was installed. Kernel coordinates are whole millionths of a millimetre; each crosses the JSON boundary as the shortest text of the double `n / 1e6` and is read back as exactly that double, which `tests/test_polygon_operations.py` checks.

`validation/check_pinned_results.py` pins these operations on every platform the programs are built for (`validation/check_installed_cam.py` pinned them on every platform a wheel was built for): an inside offset, an outside offset, a pocket and a cross-hatch fill at 33.3 degrees, generated by `kerfkite-cam`, must give the recorded digest, and so must the paths, depths and program of a V-carve (a slanted outline with an island and a block letter, 13,320 points). On Linux x86-64 the extension (GCC 13) and `kerfkite-cam` built with GCC 13, with Clang 18 and with the address and undefined-behaviour sanitizers wrote the same four programs.

Solid modelling was the fourth part computed by the core for Studio. The extension compiled the solid kernel (`native/core/src/solid/`, `solid_command.cpp`) and the polygon kernel's own command (`polygon/command.cpp`), and `studio/solid_kernel.py` gave them the interface Studio's 3D CAD modules called: parts, CAD scripts and their 2D drawings, lofts, STEP tessellations and assemblies. Unlike the operations above, a model is built in many steps, so the extension had a second entry beside `core_call`: `solid_call(request, kept)` answered with the JSON and with the solid itself, which Python kept and passed back to later requests, so no mesh crossed as text between steps. In the programs the core keeps the solid between the steps itself.

Without the extension the same modules modelled with the third-party library manifold3d, as before, and `KERFKITE_SOLID_BACKEND=manifold` selected it where the extension was installed. The two give the same shapes within nanometres, except where they facet differently (spheres, round offsets, twisted extrusions), and the kernel is slower, by a factor of 2 to 6 on most parts. When the kernel refuses a result as too fine for its grid, Studio reports the error; it never switches library for one model. [The solid kernel](SOLID-KERNEL.md#how-studio-uses-the-kernel) has the details and the measurements.

`validation/check_pinned_results.py` pins this too: a part of seven features, its section and a drawing, modelled by `kerfkite-cam`, must give the recorded digest of every vertex, triangle and outline, which the installed extension gave before. On Linux x86-64 the extension built with GCC 13, with Clang 18, and with the portable 128-bit integers a compiler without a 128-bit type uses, gave the same digest. The continuous integration workflow runs the check on Windows (MSVC), macOS (Apple Silicon and Intel) and Linux on ARM64 as well as x86-64.

The exact number formatting described above now lives in one header, `native/core/include/kerfkite/number_text.hpp`, used by the core (and by the Python extension while it existed).

The core reads and writes JSON with its own code (`native/core/include/kerfkite/json.hpp`, `native/core/src/json.cpp`), which replaced the vendored JSON for Modern C++ header; the core has no third-party source. It supports what the core uses: all of RFC 8259 on input, with every escape and surrogate pairs; numbers that keep their kind, so that `1` stays a whole number and `1.0` a float as the Python reference requires; objects with their names in byte order, the last value standing where a name repeats; and one-line output. Its limits: arrays and objects nest at most 200 deep in text that is read, text must be well-formed UTF-8 in both directions, a literal beyond the range of a double is refused, and there is no indented output, comment syntax or binary format. A float is read as the nearest double and written as the shortest text that reads back as the same double, by exact integer arithmetic in `native/core/include/kerfkite/decimal.hpp`; the C library's conversions and the C locale are not involved, and `repr` in `number_text.hpp` and `float()` of text in a project use the same code. Floats are therefore written as Python writes them. The old library wrote two things differently: a float from 1e15 up to 1e16 in exponent form (`1e+15`, now `1000000000000000.0`), and, for roughly one double in a thousand, digits that were not the shortest (`23.343139999999998`, now `23.34314`). Both forms read back as the same double.

It was checked on Linux x86-64 (GCC 13 and Clang 18) in four ways. `native/tests/json_selftest.cpp`, which CTest runs on every platform, covers each construct, the number kinds, the limits and malformed input, holds tables of doubles computed by Python, and compares every short cut in the number conversions with the exact arithmetic behind it on some 300,000 doubles and the decimals written from them. Against Python, 5 million decimal texts (ties between doubles, decimals one digit either side of a tie hundreds of places along, subnormals, exponents far outside the range) gave the double `float()` gives, and 5 million doubles gave the text `repr()` gives, with the short cuts and without them. Against the library it replaced, while that was still in the tree, 440,000 documents (generated, damaged at random, and real: fixtures, projects recorded from the test suite and the answers to them) were read by both: the same were accepted and refused, with the same values, kinds and order; equality between 87,000 pairs of values agreed; and the 26,215 jobs of the parity comparison below gave answers equal in every value and type, 97.7% of them byte for byte, the rest differing only as described above. The one deliberate difference in what is accepted, apart from the depth limit, is that text after a NUL byte is refused, where the old library stopped reading at the NUL. Under the address and undefined-behaviour sanitizers, the self-tests, 500,000 mutated documents, the comparison corpus and 2,500 jobs through `kerfkite-cam` ran without a report. Windows (MSVC), macOS and ARM64 builds have not been run; the self-test is the check for them.

`python validation/native_core_parity.py --cli <kerfkite-cam>` compares the core with the Python reference: number text, every generator call the test suite makes, and thousands of generated edge cases. A case must be reproduced exactly or declined; a different answer fails. With laser jobs ported, the measurement on Linux x86-64 is: 300,000 numbers and 360,000 distances and sums identical; 124 of 202 recorded suite calls reproduced (61%); 11,225 of 12,000 generated cases reproduced (94%), among them 1,137 laser programs; and no differences. The three benchmark programs written by `kerfkite-cam` have the same hashes as Python's.

Drilling (`native/core/src/drilling.cpp`) and drag-knife paths (`native/core/src/knife.cpp`) are ported as well. The generated cases gained 4,000 drilling and knife projects. On Linux x86-64, with those two parts: 160 of 205 recorded suite calls reproduced (78%, from 62%); 15,562 of 16,000 generated cases reproduced (97%), among them 1,290 drilling and 1,634 drag-knife programs; and no differences. The one knife case declined then was a path that returns to a point through steps too short to keep, where the Python divided by zero. That was a defect in the reference: it compared each point with the one before it in the drawing, kept or not. Both now keep a point only when it is further than 0.1 nm from the last point kept, and refuse a path that is then a single point, so the core reproduces every knife job and declines none. Knife swivels use the platform's `atan2`, `sin` and `cos`, as Python does, so they are compared on each platform against the Python there.

Ramp entries and holding tabs on router line jobs are reproduced too (`native/core/src/router_entry.cpp`, `tabs.cpp`). Before either, the reference asks Shapely whether each contour crosses itself; `simple_line.cpp` answers by the rules GEOS applies, including its double-double orientation test, and declines the rare contour for which that test and exact arithmetic disagree. A helix entry needs a pocket, so on a line job it is rejected as the reference rejects it. The ramp slope is `math.tan` of the entry angle, one C library call on each side. With these ported, the measurement on Linux x86-64 is: 161 of 205 recorded suite calls reproduced (79%); 11,432 of the same 12,000 generated cases (95%); and 5,951 of 6,005 ramp, helix and tab cases, among them 3,254 programs, the rest of those declined because they also ask for an offset, a pocket or drilling; no differences.

Helical entries into pockets are reproduced as well (`native/core/src/router_entry.cpp`). The reference placed each helix with Shapely: the pocket's region, two insets of it, the nearest point of an inset to the first point of each pass, a distance to the boundary and a covering test for the feed from the helix to the pass. The vertices of a GEOS inset cannot be reproduced to the last bit by other code, so this part was moved instead, as the offsets and pockets were: `native/core/src/pocket_entry.cpp` places the helix on the core's own polygon kernel by the same rules, the extension exposed it as the `helix` operation of `core_call('operation', ...)`, and `studio/router_entry.py` called it through `studio.operations.kernel_pocket_entries` whenever the extension was installed; `kerfkite-cam operation` answers the same request. Studio and `kerfkite-cam` therefore place the same helix by construction; the reference's Shapely code was the fallback without the extension. The centre of a helix is a double worked out with `+ - * /` alone, the same on every platform; the start angle is the platform's `atan2`, and the helix points its `sin` and `cos`, as in Python. The move also put right a fault that came with the kernel's pockets: Studio had been checking the kernel's passes, which lie on a grid of a millionth of a millimetre, against a Shapely inset to a hundredth of that, and refused most pockets with walls at an angle.

That the cutter stays clear is checked independently of both codes. `tests/test_router_entry.py` generates pockets of many shapes, with and without islands, and measures with Shapely the distance from every cutter position of the job to the contours as drawn: the centre of each helix is at least the cutter radius plus the helix radius from every wall, with no tolerance, and the feeds and passes are within 0.000002 mm of the cutter radius, the two half steps of the kernel's grid. The core's self-test makes the same check on generated pockets with a distance function of its own and compares a digest of the centres with a recorded value, and `validation/check_pinned_results.py` pins the centres `kerfkite-cam` gives, which are those an installed wheel gave.

With these, and with the drag-knife fix, the measurement on Linux x86-64 (GCC 13, Python 3.13) is: 368 of 369 recorded suite calls reproduced (219 programs and 149 rejections; the one declined is V-carving); 19,986 of 20,000 generated cases; all 6,005 ramp, helix and tab cases; and 4,998 of 5,004 pockets entered by a helix, a new group (2,189 programs and 2,809 rejections; the six declined are untidy cases whose operation was replaced with V-carving). Nothing differs, and V-carving is the only feature declined (21 cases in all).

V-carving is reproduced too, and with it every operation of a job (`native/core/src/vcarve.cpp`). The reference sampled the outlines, took Shapely's Voronoi diagram of the samples, cut it to the region and measured each point's distance to the walls. The vertices of a GEOS diagram cannot be reproduced to the last bit by other code, so this part was moved as the offsets and the helix were: the polygon kernel gained its own Delaunay triangulation and Voronoi diagram of points (`native/core/src/polygon/voronoi.cpp`: divide and conquer in O(n log n), the side-of-line test exact in 128 bits and the in-circle test in 256, vertices worked out as exact fractions and rounded to the grid, halves upwards) and the distance from a point to a region's boundary; the carve is built on them; the extension exposed it as the `vcarve` operation of `core_call('operation', ...)`, and `studio/operations.py` called it through `kernel_vcarve` whenever the extension was installed; `kerfkite-cam operation` answers the same request. The reference's Shapely code was the fallback without the extension. The method, its allowance of one sampling interval, the settings, their limits, the messages and the warning are the reference's. What the kernel adds is a defined result: samples from each ring's smallest vertex, coordinates on the grid, pieces that share an end joined into longer paths, and the paths in an order with little travel. Nothing in a carve comes from the C library but `sqrt`; the tangent of the bit's half angle is the kernel's own series. A carve of more points than a job may hold (200,000) is refused in the core with the generator's message, without being built. [The polygon kernel](POLYGON-KERNEL.md#v-carving) has the rules and the measurements.

That the bit never cuts outside the outline is checked independently of both codes. At every point of every path the circle the bit cuts at that depth, of radius `|z| tan(angle / 2)`, must be at least the sampling interval short of the nearest wall, and in the middle of every move it must still be short of the wall; the point must be in the region, and the depth within the depth of cut and the tool's radius. `tests/test_vcarve.py` and `validation/vcarve_check.py` measure this with Shapely on generated shapes (words of block letters, shapes with holes, thin strokes, flat areas, round shapes, stars), the core's self-test measures it with a distance function of its own and compares a digest of the carves with a recorded value, and `validation/check_pinned_results.py` pins the carve `kerfkite-cam` gives, which is the one an installed wheel gave. The same scripts compare the carve with Shapely's carve of the same samples, which it follows to nanometres.

With V-carving, the measurement on Linux x86-64 (GCC 13, Python 3.13) is: all 370 recorded suite calls reproduced (221 programs and 149 rejections); all 20,000 generated cases (9,737 programs and 10,263 rejections); all 6,005 ramp, helix and tab cases; all 5,004 pockets entered by a helix; and all 4,010 V-carves, a new group (2,366 programs and 1,644 rejections). Nothing differs and nothing is declined: in this run every case was reproduced. The core can still decline an input, never an operation: a number written in non-ASCII digits or beyond the range of a double, a contour whose self-crossing test turns on rounding inside GEOS or passes the bound on work, and a few degenerate contours under tabs and ramps. `validation/vcarve_check.py` on 4,000 generated projects carved 2,287 shapes: at every point the cut was at least 1.0000 sampling intervals short of the nearest wall and in the middle of every move at least 0.5082; against Shapely's carve of the same samples no point of either carve was further than 2.2 nm from the other and the total lengths agreed to 2.1 parts in a million. `kerfkite-cam` built with GCC 13, with Clang 18, with the kernel's own 128-bit integer throughout (the one a compiler without a 128-bit type uses) and under the address and undefined-behaviour sanitizers gave the same bytes for 1,114 generated jobs, 810 of them V-carves, and each build passed the self-tests with their recorded digests. Windows (MSVC), macOS and ARM64 builds have not been run; the digests in the self-tests and the installed-wheel check are what test them.

The test of whether a contour crosses itself (`native/core/src/simple_line.cpp`) has a bounded worst case. It used to apply GEOS's test to every pair of segments whose bounding boxes overlap. For a contour of long segments side by side that is every pair: a comb of 20,000 parallel strokes took 2.1 s and one of 100,000, the most a job may hold, about a minute; a fan of rays and a square spiral behaved alike. (A contour that does cross was never slow: the first crossing found ends the test.) Two things bound it now.

* A tree over the segments, walked two branches at a time. A pair of branches is left out whole when GEOS's test is certain to pass every pair of segments in it: when the boxes of the two branches are apart, or when every end point in one branch is clear of, and on one side of, the line of every segment in the other. The second holds because GEOS passes two segments as soon as its orientation test puts both ends of one strictly on one side of the other, and that test is exact whenever its floating-point filter settles the sign; the tree asks for three times the margin the filter needs, at every corner of the boxes of end points, and the determinant is of the first degree in each coordinate, so the corners bound it. The branches are split on whichever coordinate of the segments' first or second end points is most spread, which keeps those boxes small for combs, fans and spirals alike. The same contours of 100,000 segments now take 0.05 to 0.12 s.
* A count of the work, in fixed units of a few nanoseconds each. Past 400 million units, about a second, the contour is refused (declined as not ported with the reference's rules in force). The count does not depend on the machine, so the tests bound it without timing anything: the self-test requires a multiple of n log n for long simple lines of five kinds, and that a contour past a small budget is declined at once.

The answer is unchanged. `validation/native_core_parity.py` compares it with Shapely's `is_simple` for 20,000 lines by each of three methods (the usual one, the tree forced on short lines, and every pair): points on coarse grids, random points, points in a line, and regular lines of 50 to 400 points spoilt by one touch, crossing, overlap, repeated vertex or a vertex a few units in the last place off another segment, with strokes from far apart down to a few units in the last place apart. A further 400,000 lines from other seeds were compared the same way while this was written. The tree and the test of every pair meet the pairs in different orders, so on the rare contour whose answer depends on rounding inside GEOS one may decline where the other answers; where both answer they agree.
