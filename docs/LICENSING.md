The native core has no third-party source of its own. Its JSON reader and writer (`native/core/include/kerfkite/json.hpp`, `native/core/src/json.cpp`) and the decimal conversions under them (`native/core/include/kerfkite/decimal.hpp`) are first-party code under the project's MIT licence, written from RFC 8259 and from the published methods named in those files. They replace JSON for Modern C++ 3.11.3 (MIT), which the source tree used to vendor as `native/third_party/nlohmann/json.hpp`. A `kerfkite-cam` binary or compiled extension built from a revision that still has that header contains it and must keep its licence file. The one third-party library the core still builds with is GEOS, described next; replacing it is separate work.

**GEOS in the native core.** With the default build options `kerfkite-cam` contains GEOS 3.14.1, the same release the Shapely 2.2.0 wheels carry, so that the core and the Python reference compute polygons with the same library. GEOS is licensed under the GNU LGPL, version 2.1. Its source is not in this repository: the build downloads the upstream release tarball, checks its SHA-256 and compiles it unmodified (`native/cmake/geos.cmake`). The licence text is kept at `native/third_party/geos/COPYING`. The Python wheels, the compiled extension and the Pocket APK do not contain this copy of GEOS. [GEOS 3.14.1 release](https://github.com/libgeos/geos/releases/tag/3.14.1)

By default GEOS is linked statically into the program. LGPL 2.1 allows a program under another licence to be distributed linked with the library, on conditions (section 6): the recipient is told that the program uses GEOS and that GEOS is under the LGPL, receives the licence text and GEOS's source or a written offer of it, and is able to modify GEOS and relink the program with the modified library. For a statically linked program the last condition means supplying what is needed to relink: the program's own source or object files for exactly that build. KerfKite's source is public under MIT, which permits modification and rebuilding, so a recipient who has the source of the released version and the pinned GEOS tarball can rebuild `kerfkite-cam` against a changed GEOS. The licence's terms must also not forbid modification for the recipient's own use or reverse engineering to debug such modifications; MIT forbids neither.

Two build options change how GEOS is combined with the program. `-DKERFKITE_GEOS_SHARED=ON` builds GEOS as shared libraries placed beside `kerfkite-cam`, which a recipient can replace with a compatible build without relinking (the arrangement section 6b describes). `-DKERFKITE_SYSTEM_GEOS=ON` links a GEOS 3.14.1 already installed on the system. `-DKERFKITE_WITH_GEOS=OFF` leaves GEOS out; the polygon operations are then declined.

**Open decision for the project owner.** No binary containing GEOS has been published by this project yet. Before one is (a release of `kerfkite-cam`, an installer or an app that embeds the core), the owner needs to choose between static linking and the shared-library build, and each distributed package then needs: a notice that it contains GEOS under LGPL 2.1, the licence text, GEOS's copyright notices where the program shows its own, the GEOS 3.14.1 source or a written offer of it, and, for a static build, the KerfKite source of exactly that release kept available. This paragraph describes what the build does and what the licence asks; it is not legal advice, and the choice has not been reviewed by a lawyer. Platforms that do not let a user replace a library inside an installed application, such as phone app stores, need particular care with either arrangement.

To refresh the inventory in a build environment, run `python -m pip install --dry-run --ignore-installed --report resolved.json ".[web,step,mcp]"`. Use the target OS, architecture and Python for each build, inspect the actual archives, and retain licence files even when a package's metadata reports a single permissive identifier. The recorded resolver output describes a specific platform and date.
