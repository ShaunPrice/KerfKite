# Changelog

Notable changes to KerfKite Studio and KerfKite Pocket. Versions before this file was introduced are described in the [GitHub release notes](https://github.com/ShaunPrice/KerfKite/releases) and the [release review](docs/RELEASE-REVIEW.md).

## Unreleased

### Added
- **Machine setup tools.** **Control → Machine setup tools** finds work zero on a touch plate (Z alone, or X, Y and Z on a corner plate, each touched twice), lists the controller's numbered settings and writes one at a time with a read-back, corrects an axis's steps per millimetre from a measured move, adds a spoilboard surfacing job to the design, and keeps and runs operator macros of plain G-code. The workstation server gains `GET /api/setup` and `POST /api/setup/probe`, `/setting` and `/macro`, which need the controller idle and the operator's confirmation; the Grbl simulator gains relative moves, a touch plate and settings that keep what is written. Exercised on the simulator only. See [Machine setup tools](docs/SETUP-TOOLS.md).
- **Tiling an oversized job.** **CAM → Tile an oversized job** divides a router job larger than the machine into a program for each tile, with the tile's corner as X0 Y0: cuts are kept where they lie in the tile, with a retract where one leaves and a plunge where one enters. A tile is exported, or run at the workstation with the usual confirmation. In the core as `kerfkite-cam tile`, with `POST /api/tile` and a `tile` field of `POST /api/run`. See [Tiling an oversized job](docs/TILING.md).
- **Roughing a 3D relief.** **3D relief → Roughing first** adds passes that take the stock down level by level with a flat cutter and leave an allowance, ahead of the finishing relief of an image or an STL. No pass goes below the roughing cutter's contact, and each takes at most one step of depth. Roughing and finishing get tool identities for a stage file each. In the core as `kerfkite-cam relief-roughing`, with `POST /api/relief-roughing`. See [Roughing a 3D relief](docs/RELIEF-ROUGHING.md).
- **Dog-bone corners, inlays and nesting.** **Design → Joinery & nesting** relieves the corners a round cutter cannot reach (inside an opening, or round a part), makes a pocket and a matching plug from a shape with a clearance all round, and nests the parts whose output is on with a gap and a margin. See [Joinery, inlays and nesting](docs/JOINERY.md).
- **Pen drawing.** A fourth machine head, **Pen · drawing**, draws with a spring-loaded pen in place of the cutter or the laser. The pen is lifted by the Z axis, with the spindle never started, or by a servo or solenoid on the spindle or laser output, with Z never moved. It draws lines and hatch fill, goes over lines as often as asked, and can imitate a broad calligraphy nib with a fine pen. In the core as `"mode": "pen"`; the editor's offline generator writes the same programs. See [Drawing with a pen](docs/PEN.md).
- **Pen drawing round a cylinder.** A pen job can be wrapped on a rotary axis like a router job, for either way of lifting the pen. A servo pen draws at the surface with the radial axis never moved, and a holder that needs a signal to stay up ends the program raised. See [Round a cylinder](docs/PEN.md#round-a-cylinder).
- **Adaptive clearing for relief roughing.** **3D relief → Roughing first** offers a second strategy that keeps the width of cut near a figure you set: at each level the cutter goes down a helix and peels the stock away, instead of running through it at its full width. Slopes are left in steps and walls keep a little more than the allowance; both are stated in the message. In the core as `"rough_strategy": "adaptive"` of `kerfkite-cam relief-roughing` and `POST /api/relief-roughing`. See [Roughing a 3D relief](docs/RELIEF-ROUGHING.md#adaptive-clearing).
- **V-carved inlays.** **Design → Joinery & nesting → Inlay** makes a V-carved pocket and a mirrored plug with clearing for each, sized so that the plug goes in by a set depth and leaves a gap for glue. V-carving gains `v_start_depth`, which carves an outline below the stock top. See [Joinery, inlays and nesting](docs/JOINERY.md#v-carved-for-a-v-bit).
- **Nesting by outline, with turning.** **Nest parts** places parts by their own outlines, so that one sits in the hollow of another, and may turn them by quarter turns or in steps of 45° or 15°, or not at all where grain matters. The gap is kept between the outlines themselves.
- **Tiling for laser and knife jobs.** A laser job is divided with the beam on only inside a tile's cuts, and a knife job as a router job is.
- **Touch plate and settings on Marlin.** The touch plate sets work zero with `G92` on a Marlin controller, and its `M92`, `M203` and `M201` settings are listed, written, read back and stored with `M500` when asked. A zeroing program stops at a command the firmware does not know.
- **Project wizards.** **Templates → Project wizards** draws a finger-jointed box (with or without a lid, with a fit allowance and dog-boned slots for a router), slot-together dividers and a sign blank with hanging holes, laid out on the sheet with outside profiles. See [Project wizards](docs/PROJECT-WIZARDS.md).
- **Tool library with starting feeds and speeds.** **CAM → Tool library** keeps the cutters you own (twelve to start with, up to 200, exported and imported as `kerfkite-tools/1`) and works out a spindle speed, feed, plunge, step down and stepover for one of them in ten materials, from chip load, the cutting speed of the material and a description of the machine: its rigidity, spindle range and fastest cutting feed. **Use these settings** fills the CAM fields and the manual tool-change identity; nothing reaches a controller. The values are starting points to test on scrap, not tested recipes. See [Tool library and starting feeds](docs/TOOL-LIBRARY.md).

## 0.7.0 — 2026-11-24

Studio 0.7.0 is the first release in which every part of Studio is a native program and no Python is installed, downloaded or run. Some entries below mention the compiled extension, the wheels, Shapely, manifold3d, GEOS or the `cryptography` package. Those entries record steps taken while the Python service was still in place. In 0.7.0 the native programs always do that work, the wheels are no longer published, and the phone pendant's HTTPS comes from the relay `kerfkite-pendant-tls`, which uses Go's standard library and no `cryptography` package.

### Changed
- **Studio is the native programs; Python is removed.** The Python service (`studio/*.py`), its compiled extension, `setup.py` and the package metadata are gone, and with them every Python dependency of Studio (Flask, pyserial, Shapely, NumPy, manifold3d, ezdxf, pypdf, cheroot, cryptography, FastMCP, OCP). The workstation server `kerfkite-studio`, the HTTPS editor `kerfkite-web`, the MCP assistant server `kerfkite-mcp`, `kerfkite-cam` and the STEP add-on `kerfkite-step` do all of its work. The Python reference, its tests and the harnesses that compared the programs with it are kept at the last commit that had them, and continuous integration runs those comparisons from there against every build ([The Python reference](docs/DEVELOPER.md#the-python-reference)).
- The desktop packages carry only the native programs. The launcher starts `kerfkite-studio`, sets up no Python runtime and downloads nothing on its first start; its private-Python path, the uv download and the setup page's STEP download are gone. `packaging/desktop/build.py` packages the folders of the **Build the desktop programs and installers** workflow (the wheel argument and `--native` are gone), and the wheel workflow and its locked requirements are removed. The browser-only SBC package is made from `studio/static`. Studio's version is in `VERSION`, which CMake and the packaging read. From a source checkout, `scripts/install.sh` and `install.ps1` build the C++ programs with their self-tests, and `start.sh` and `start.bat` start `kerfkite-studio`. The installer smoke test expects a native package, and CI runs `validation/check_installed_cam.py`, which the wheel builds ran.
- The native core answers by rules of its own where it declined to the Python for want of one: the C++ server and `kerfkite-cam` no longer answer "is read by Studio's Python ..." for any input. Contours whose self-crossing test turns on rounding inside GEOS get the exact answer (in integers for subnormal and huge coordinates), and one that needs too much work is refused; DXF splines given only by fit points are interpolated as CAD programs and ezdxf interpolate them (a cubic B-spline through the points with chord-length parameters, the given end tangents or none), and a repeated fit point is passed through once; PDF files that depart from the usual form are read as the PDF format says or as readers commonly repair them (stream lengths from `endstream`, `startxref` by search, looser cross-reference entries, hybrid cross-references, inline images skipped, names and strings with escapes, references to objects that are not there as null), and otherwise refused with the reference's messages; dimension expressions outside the core's grammar, touching surface loops and STEP features in `kerfkite-cam` are refused with clear messages; coordinates and placements are written exactly for every double. Studio's Python keeps the reference's rules through the extension, so the Python service still answers those cases itself. `kerfkite-cam batch --own`, an own-rules pass in `validation/native_core_parity.py` and the `X-KerfKite-Own-Rule` header of a server started with `KERFKITE_PARITY=1` keep the comparisons honest. See [The core's own rules](docs/NATIVE.md#the-cores-own-rules).
- LightBurn bundles are read by the native core whatever their archive holds: ZIP64 end records and extra fields and Info-ZIP Unicode path fields are read as Python 3.13's zipfile reads them, and entries that share a header are read, as zipfile does with a warning. An entry that needs a ZIP version above 6.3, patched or strongly encrypted data and a member header before the start of the data are refused as an unreadable bundle, where the Python stopped with an error that was no refusal; a member's DEFLATE data is read no further than the 4 MB a member may hold. Nothing is declined to the Python any more; 10,504 generated cases were reproduced or answered so, none different. See [LightBurn bundles](docs/NATIVE.md#lightburn-bundles).
- The native core answers more of what it declined to the Python. `float()` of text reads digits of every script, as Python's does, so a feed of fullwidth 600 is 600; a stock preview row of text `float()` cannot read is refused with `float()`'s own message (`repr()` and all); base64 with `=` after its last whole group is refused, as Python 3.12.10 and later refuse it; and on Windows a UNC drawing name's anchor is no part of its name. Where the Python stopped with an exception that was no refusal, the core now refuses: a tool-change stage too short to end retracted, a ramp entry along a contour of no length, a rotary job whose warnings are not a list, a sketch outline of fewer than three points. States the checks before them rule out (holding tabs before the seam, feeds beyond `round()`'s range) are internal errors instead of declines.
- The native core reads text that is not ASCII in foreign drawings and fixture checks, which it declined to the Python before: posted G-code, HP-GL and LinuxCNC INI files with comments in other languages, other spaces and line boundaries, and digits of other scripts are read as Python's `str` methods and `re` read them, and the messages name what they quote as the Python did. `validation/native_core_parity.py` now puts such text in its drawings and programs and reproduced all 18,625 drawings and 8,000 checks. A rotary source that is not ASCII is refused (**Rotary source G-code must be ASCII text**): the Python read digits and spaces of other scripts there and copied them into the program a controller runs.
- The Linux desktop window is a C program on GTK 3 (`packaging/desktop/linux/`) in place of the Python GTK script, so the Debian package no longer depends on Python or its GTK bindings. It finds WebKitGTK 4.1, or else 4.0, when it starts; `kerfkite-native --check` reports which. Menus, toolbar, inspector, file dialogs, downloads and the help and print windows behave as before. Its smoke test (`kerfkite-native-smoke`, built from the same sources) drives the window against the C++ workstation server under a virtual display in CI.

The relay's `-fetch` now answers with the head's lines and headers, keeps a body cut short of its length as Python's http.client did, and checks a CA file on its own (`check_only`). `validation/mcp_parity.py`, `mcp_workshop_parity.py` and the new `mcp_remote_parity.py` compare it with the Python server; [the assistant server](docs/NATIVE.md#the-assistant-server) lists its own rules. `--transport http` serves the hosted workshop as FastMCP's stateless HTTP transport does, on the loopback interface behind the operator's HTTPS proxy: its Host and Origin guard, the protected-resource metadata and its CORS, the SDK's checks of each POST, and RS256 OAuth tokens accepted as FastMCP's JWTVerifier and joserfc accept them, the signature checked by the system's cryptography (CNG, the Security framework or libcrypto) and the issuer's key set fetched by the relay only from public addresses (`-fetch` now takes a TLS name and a Host header for an address resolved beforehand). `validation/mcp_http_parity.py` compares both transports with the Python server's, in network namespaces of its own with stand-ins for the key sets. - LightBurn user bundles are read by the native core (`native/core/src/bundle_import.cpp`, the port of `studio/import_bundle.py`), without zipfile or zlib: `/api/import-bundle` sends the core's answer and `kerfkite-cam bundle-import` lists a bundle or reads a member without Python. The core reads the ZIP archive as Python's zipfile reads it, inflates members with its own inflate (which now reports the errors zlib reports), and gives the reference's listing, text and messages to the bit; ZIP64 archives, newer entry versions and members that inflate past 4 MB stay with the Python. 36,000 generated requests were reproduced or declined, none different. See [LightBurn bundles](docs/NATIVE.md#lightburn-bundles).
- PDF pages are read by the native core (`native/core/src/pdf_import.cpp`, the port of `studio/pdf_import.py`), without pypdf or Shapely: `/api/pdf-import` sends the core's answer and `kerfkite-cam pdf-import` reads a page without Python. The core reads the PDF format itself, with its own inflate for FlateDecode, and gives the reference's draft, warnings and messages to the bit; files pypdf would repair, encrypted files other than the standard RC4 ones, and pages with inline images stay with the Python. 20,000 generated pages were reproduced or declined, none different. See [PDF pages](docs/NATIVE.md#pdf-pages).
- Foreign drawings are read by the native core (`native/core/src/program_import.cpp`, the port of `studio/program_import.py`). `/api/program-import` sends the core's answer for posted G-code, HP-GL plots and LinuxCNC INI files, and `kerfkite-cam program-import` reads them without Python. The artwork, layers, presets, workspace, warnings and every message are the Python's to the bit, including Python's `float()`, `round()` and `{:g}`. The comparison replays 3,000 generated files by default and the suite's own; 18,493 distinct cases from 20,000 files matched or were declined. Program text that is not ASCII stays with the Python reader. See [Foreign drawings](docs/NATIVE.md#foreign-drawings).
- DXF drawings are read by the native core's own DXF reader (`native/core/src/dxf.cpp`), Studio's reader wherever the compiled extension is installed; the ezdxf reader stays as the reference and the fallback. Layers, colours, objects, warnings and refusals are the reference's. The outlines differ in their vertices: the core flattens the true curves to 0.025 mm, with about a third fewer vertices, and draws rational splines, splines of degree 1 and 2, and closed splines correctly, where the reference was millimetres off or, for closed splines, drew far outside the drawing and refused it. Units the reference could not convert (microinches, mils, US survey units) are read. `validation/dxf_import_check.py` compares the two; 4,500 generated drawings agreed within its bounds. A spline given only by fit points is still read by the Python.
- Assemblies are solved by the native core (`native/core/src/assembly.cpp`), the implementation Studio now uses for `/api/assembly/solve`. The mate tree, the additional mates fitted on the joints' free axes, the parts, contacts, interferences and every message follow the Python. The matrix arithmetic is the core's own, so placements agree with NumPy's to rounding: to 10⁻¹² mm without additional mates, and within the fit's 10⁻⁶ mm tolerance with them. `kerfkite-cam assembly-solve` solves an assembly without Python, and `validation/assembly_check.py` compares the two. See [Assemblies](docs/NATIVE.md#assemblies).
- Sketch constraints are solved by the native core, and its solver is the one Studio uses. It is the Python's Gauss-Newton iteration statement for statement, with its own least squares by a singular value decomposition in place of NumPy's LAPACK. The vertices agree with NumPy's to rounding, not to the bit: on 6,000 generated sketches the largest difference was 7.3·10⁻⁷ mm. Where a system is ill-conditioned the two can take different paths, which NumPy's own answer also does from one BLAS library to another. Constrained sketches are now rebuilt by the native core with the rest of the history. `kerfkite-cam sketch-solve` solves a sketch without Python, and `validation/sketch_constraint_check.py` compares the two solvers. See [Sketch constraints](docs/NATIVE.md#sketch-constraints).
- CAD scripts run in the native core (`native/core/src/scad.cpp`, the port of `studio/scad_language.py` and `studio/scad_geometry.py`). `/api/cad-script` sends the core's answer, the scripted features of a parametric solid are rebuilt by it, and `kerfkite-cam cad-script` previews a script without Python. The reader, the evaluator and the geometry are the Python's to the bit. That covers Python's ints and floats, its equality and its `sum()`, CPython's maths functions, the evaluation budget charged unit for unit, every request to the kernels and every message with its line and column. The comparison replays 1,000 generated scripts and the suite's own, and every one matched. Two thresholds that the Python leaves to NumPy's platform-dependent linear algebra (a singular `multmatrix()`, a polyhedron face's area and flatness) can be judged differently only within rounding of the threshold. See [CAD scripts](docs/NATIVE.md#cad-scripts).
- Lofts between rectangles, ellipses and circles are rebuilt by the native core too, with the Python's mesh to the bit.
- Sketched extrusions and revolutions are rebuilt by the native core as well: the sketch's vertices, fillets, cubic edges with tangent alignment and every refusal of the profile, checked as Shapely checks it and identical to the Python to the bit. STEP parts stay with the Python. See [Parametric solids](docs/NATIVE.md#parametric-solids).
- The parametric solid history is rebuilt by the native core (`native/core/src/solid_cad.cpp`), the first part of Studio's 3D CAD front end to leave Python. `/api/solid-cad` and `/api/solid-cad/section` send the core's answer. `kerfkite-cam solid-cad` and `solid-cad-section` rebuild a model without Python. Parameters, dimension expressions, boxes, cylinders, spheres, patterns, runs of Boolean operations and sections are covered, and they ask the solid kernel for the same operations as the Python, so meshes, volumes and outlines are identical to the bit. Sketched, lofted and scripted features and sketch constraints followed (see above); STEP parts and expressions outside the small grammar the core reads are left to the Python. The parity comparison now replays the test suite's solid calls and 300 generated histories. See [Parametric solids](docs/NATIVE.md#parametric-solids).
- Artwork reliefs are rasterised in the native core, on KerfKite's own polygon kernel (`native/core/src/artwork_relief.cpp`), as the one implementation. `/api/artwork-relief` sends the core's answer, and `kerfkite-cam artwork-relief` makes a relief from artwork without Python. Each cell is decided exactly on the kernel's grid of a millionth of a millimetre. Compared with the Shapely reference on 500 generated cases, every refusal was the same, and cells differed only where the outline lies within two millionths of a millimetre of a cell's edge (2,808 of 1,862,733 cells). The core took 0.14 s where Shapely took 14.7 s. Shapely stays as the reference and as the fallback without the extension. See [Artwork reliefs](docs/NATIVE.md#artwork-reliefs).
- Studio measures this computer's relief contact each time it starts and shares large jobs between the GPU and the processor. A background calibration (`kerfkite::relief_calibrate`, `kerfkite-cam calibrate`) times one job on all the threads, on the GPU alone and on both at once (beside all the threads and beside one fewer, for processors with few cores), comparing every run with the threads' answer bit for bit. Large jobs then go the way the measurements favour, with the GPU taking the first rasters up to the share at which both finish together; the depths are the threads' bits whatever the share. On a 24-thread laptop with an RTX 5090 Laptop GPU a relief from a 1024-point image with a 12 mm ball now takes 103 ms instead of 126 ms on the GPU alone, and capped at 4 threads 116 ms instead of 472 ms on the threads alone. An integrated GPU is now considered too, but used only where the calibration measured a gain; without a GPU that has double precision, as on a Raspberry Pi, the calibration measures the threads only, in about a tenth of a second. The editor reports **on the GPU and processor together** when the two shared a job. See [Threads, and a GPU for large reliefs](docs/NATIVE.md#threads-and-a-gpu-for-large-reliefs).
- KerfKite Studio is easy to find after installation. Windows Setup always adds it to Start and now offers a desktop shortcut on a components page, ticked; the uninstaller removes it. On its first start the desktop launcher offers a desktop shortcut on macOS and Linux, and on the portable Linux archive an entry in the applications menu, so later starts no longer need the extracted folder; both are ticked and can be added later from the launcher. A Mac app opened straight from its disk image tells the user to drag it to Applications first. Shortcuts the launcher made follow the application when its folder moves. See [Install KerfKite Studio](docs/INSTALL.md#desktop-or-phone-installation).
- Studio generates G-code and rotary programs in the native core. `generate`, `generate_rotary` and `wrap_job` hand the request to the core through the extension and return its job, which carries everything the Python job had, including the paths and depths cut, the holes and drill of a drilling job and the operation count of an ordered one. The programs are byte for byte the same; the Python modules stay as the reference and answer what the core declines or what JSON cannot carry unchanged. On the benchmark jobs the laser job takes 26 ms instead of 93 ms and the rotary job 114 ms instead of 129 ms, and a preview of a 135,886-line relief returns in 129 ms instead of 329 ms (a rotary preview in 193 ms instead of 412 ms), because the core writes the JSON of the preview itself. `KERFKITE_GCODE_BACKEND=python` still selects the Python CAM, and so does `KERFKITE_POLYGON_BACKEND=shapely`. ### Changed
- Relief contact and the stock preview use every thread of the processor, with the same result to the last bit as on one thread: rasters or map rows are shared out in fixed runs, each value written by one thread with unchanged arithmetic, and errors found in the order one thread meets them. `KERFKITE_THREADS` caps the threads. On a 24-thread laptop the contact of a relief from a 1024-point map with a 12 mm ball takes 116 ms instead of 1.77 s on one thread; on a two-core machine both threads take about half the time of one. The inner loop also reads cell edges from a table worked out once per job, which makes one thread 19 to 25 per cent faster with the same digests. With the compiled extension, image reliefs take maps of up to 1024 points a side instead of 128 in the editor and 256 at the server, and jobs of up to 2 × 10⁹ contact checks instead of 10⁷; the editor sends large maps as RGB bytes. STL and artwork reliefs stay at 128. See [Threads and the GPU](docs/NATIVE.md#threads-and-a-gpu-for-large-reliefs).
- Large reliefs may run on a discrete GPU, on Windows and Linux. KerfKite loads the system's OpenCL library when a job is large enough (nothing of OpenCL is compiled in or shipped), takes a discrete GPU with double precision, and runs the contact arithmetic statement for statement in OpenCL C, so the depths are the processor's to the last bit; 128 contacts of every result are computed again on the processor and compared, and any difference turns the GPU off. A GPU is set up only once the large jobs of a session have spent as long on the threads as setting it up takes (0.1 to 0.3 s), and each job then goes to whichever has been measured faster. Work goes in slices of about 50 ms, so a slow device cannot trigger a display driver reset. The editor reports **C++ accelerated relief on the GPU**, and `KERFKITE_GPU=auto|on|off` controls the choice. On the large jobs an RTX 5090 Laptop GPU was 5 to 15 per cent faster than all 24 threads of its laptop, 2.1 to 2.4 times faster than 8 threads and 3.5 to 4.1 times faster than 4. Integrated GPUs are left out: the laptop's own was nine times slower than its threads. The stock preview stays on the processor, because its `hypot` and `tan` differ in the last bits between GPUs.
- Solid models rebuild faster, and the solids are the same. Studio applies consecutive features of one operation together, as one batch Boolean operation (cuts as the solid less the union of their tools), on either backend; if a batch fails or its result is empty or too large, the run is repeated feature by feature so that the error names the feature. The kernel triangulates faces by Delaunay insertion in the order of a Hilbert curve, recognises crossing triangles that do not meet from their corners, and composes unions of solids whose boxes do not meet. Through Studio a plate with 60 bores, one feature each, rebuilds in 357 ms instead of 1.94 s, and one with 64 bores in eight patterns in 390 ms instead of 1.45 s, on a two-core machine. Every replayed operation of 1500 generated models gives the same set of points or differs only by what the 1 nm grid cannot hold (thickest layer 0.15 nm); faces may be divided into other triangles, and the self-test's recorded digest changes once to `e150789607e7145b`. A new tool, `kerfkite_solid_shapes`, compares two builds of the kernel as solids. See [Stage two](docs/SOLID-KERNEL.md#stage-two-the-same-solids-divided-differently).
- Studio's 3D CAD now runs on KerfKite's own code instead of the third-party library manifold3d. Wherever the compiled extension is installed, parts, CAD scripts, lofts, STEP tessellations and assemblies are modelled by the solid kernel of the native core, and the 2D drawings of CAD scripts by its polygon kernel, which gained the corners a drawing asks for (arcs with their vertices on the true arc, miters with a limit, bevels), a convex hull and affine maps. The shapes are the same within nanometres. What a user can notice: coordinates are whole nanometres (`14.65`, not `14.649999998509884`); a sphere is faceted in bands of latitude and has about twice the triangles for the same `$fn`, so models with many spheres reach the triangle limits sooner; a round `offset(r=…)` divides its arcs into equal parts; a twisted extrusion may split its sides along the other diagonal, which changes its volume when there are few slices; section outlines have no points along straight sides; and rebuilding is slower, by a factor of 2 to 6 on most of the parts measured and 14 on a pattern of bores that overlap one another (a plate with a bore 4 ms against 2 ms; a part of seven features with a sphere and tapered bores 0.29 s against 0.05 s, on a two-core machine). The kernel refuses a result it cannot represent on its 1 nm grid, which can happen where two faces almost coincide after a turn; Studio then reports an error naming the feature or script line, and never switches library for one model. The differences, the measurements and the comparison of the two over every model of the tests and the scripting guide are in [The solid kernel](docs/SOLID-KERNEL.md#how-studio-uses-the-kernel).
- The solid kernel was made two to seven times faster after it was first written, with no result changed: every recorded digest of its meshes is what it was, and every answer of the `solid` command on the models measured is the same to the last character. Through Studio a plate with a bore rebuilds in 4 ms where it took 11 ms, the seven-feature part in 0.29 s where it took 1.23 s, and a plate with 60 bores added one at a time in 2.2 s where it took 13.3 s. The time went into exact work whose answer was already certain: crossing points computed for pairs of triangles that then proved not to meet, triangles looked up against their own solid, big-integer determinants for points known to share a plane or a line, and a check of the rounded result that built everything a full intersection builds. Those are now avoided or answered first by a test in doubles with a proven error bound, which falls back to the integers whenever it is not certain. Each such way is tested against the computation it stands in for, and whole operations are computed both ways and compared (`kerfkite_solid_selftest --plain N SEED`). `kerfkite_solid_bench` times twelve models on the kernel alone and `validation/benchmark_solid.py` times them through Studio on the kernel and on manifold3d. A mesh now crosses from the kernel to numpy as bytes. The measurements, the bounds and what is left are in [The solid kernel](docs/SOLID-KERNEL.md#performance).
- An installation without the compiled extension (the portable wheel) still models solids and script drawings with manifold3d, which remains a dependency. `KERFKITE_SOLID_BACKEND=manifold` selects that library deliberately where the extension is installed, and `=kernel` refuses to run without the extension.
- The installed-wheel check carves a slanted outline with an island and a block letter through the extension and compares every path, depth and program line with a recorded digest. Nothing behind a carve comes from the C library but `sqrt`, so every wheel must give the same bytes.
- The compiled extension carries the solid kernel, and the installed-wheel check models a part and a drawing through it and compares every vertex, triangle and outline with a recorded digest, so each wheel and installer proves on its own platform that it has the kernel and that the kernel gives the same bytes there.
- A horizontal section through a solid has a point at each corner and none inside a flat face, however the face is triangulated.
- Offsets, pockets and hatch fills now come from KerfKite's own geometry code instead of the GEOS library. Studio uses it whenever its compiled extension is installed, and `kerfkite-cam` always does, so the two write the same program for the same job. The regions cut are the same as before. The tool paths differ from those of earlier versions in where their vertices fall, by amounts far below machining accuracy: coordinates sit on a grid of a millionth of a millimetre, and at round corners the path is at most 0.034% of the offset distance outside the exact offset (half a micrometre for a 3.175 mm cutter). Arcs are approximated from outside, so the tool is never nearer to the contour than its radius; before, it could be up to 0.03% of the radius nearer. Pockets have far fewer vertices, so their programs are shorter. Other visible differences: each offset or pocket contour now starts at its left-most point, and leads, ramp entries and tabs on it are placed from there; a hatch row that runs along an edge of the shape now runs in the same direction as its neighbouring rows; pieces of a hatch row shorter than 0.001 mm, which the program's three decimals could not express, are left out; and a contour whose last point is within a millionth of a millimetre of its first, but not equal to it, is now cut where it was often refused as self-crossing. Settings, their limits, messages and warnings are unchanged. See [The polygon kernel](docs/POLYGON-KERNEL.md).
- The place where a helix descends into a pocket is now found by KerfKite's own geometry code as well, whenever the compiled extension is installed, so Studio and `kerfkite-cam` write the same helical entry. The rules are the ones Studio had: the helix is centred on the first point of a pass where that point is clear, and otherwise at the nearest point that is at least the cutter radius plus the helix radius (plus 0.001 mm and 0.04% of the two) from every wall and island; the feed from the helix to the pass must stay inside the region the cutter's centre may occupy. Programs with a helical pocket entry differ from those of earlier versions in the last digits of where a helix beside a wall is centred (under 0.01 mm in the cases compared), because the two libraries round a corner differently. The cutter is never nearer a wall than its radius: the helix keeps at least 0.001 mm more than that, and the feed and the passes keep it to within the two millionths of a millimetre of the kernel's grid. One thing is put right by this: since pockets moved to KerfKite's own code, Studio checked the feed against a Shapely offset to a hundred-millionth of a millimetre, while the passes it checked were on the kernel's grid of a millionth of a millimetre; a pass could lie that far outside the Shapely offset, so most pockets with walls at an angle were refused with `No clear helix and connecting feed to this pocket contour`. Without the extension the Shapely code is used as before, for the helix and the pocket alike.
- V-carving now comes from KerfKite's own geometry code instead of Shapely's Voronoi diagram, whenever the compiled extension is installed, so Studio and `kerfkite-cam` write the same carve. What is cut is the same: the outlines are sampled every sampling interval, the Voronoi diagram of the samples is cut to the shape, and at each point the bit goes as deep as fits between the walls less one sampling interval, within the depth of cut and the tool's radius. The settings (`v_resolution`, `v_angle`, `depth`, `tool_diameter`), their limits, the messages and the warning are unchanged. **V-carve toolpaths differ from those of earlier versions in where their points fall and in their order**:
  - The samples start at the left-most vertex of each outline, where they used to start wherever the geometry library began the ring, so the spokes between the centre line and the walls stand elsewhere along the walls, by up to half a sampling interval. Measured over 2,281 generated shapes against the earlier code: where either carve cuts a circle at least one interval in radius, the other has a path within 0.2 intervals in the middle shape and within 2 intervals in 95% of shapes; within half an interval in every shape with no corner turning inwards; and up to 5.4 intervals round a corner that turns inwards, where the paths of this method have always stood further apart than the interval. The total length cut was 0.18% greater in all; a shape that barely cuts at all in one carve may not cut in the other.
  - Given the same samples the new carve and Shapely's are the same to 2.2 nm, which is how the new diagram was checked.
  - Coordinates sit on a grid of a millionth of a millimetre, and the depths no longer depend on the C library's tangent.
  - Pieces that meet end to end are joined into longer paths, so the tool lifts about half as often (184,039 paths in place of 401,030 over those shapes), and the paths are ordered so that each starts near where the last ended: travel between paths fell to 16% (for 24 block letters 12 mm tall sampled every 0.3 mm, 1.6 m in place of 43.8 m, for 4.3 m of cutting). The centre line of a stroke is one path; a path may run in either direction.
  - A carve of more than 200,000 points, which no job may hold, is refused with `Job exceeds 200,000 cutting segments` before it is built, where it used to be measured point by point first. A job that is also wrong in another way (a ramp entry on a V-carve, say) may now be refused for the limit.

  That the bit never cuts outside the outline is checked with Shapely as an independent measure: at every point of every path the cut is at least one sampling interval short of the nearest wall, and in the middle of every move at least half an interval. See [V-carving](docs/POLYGON-KERNEL.md#v-carving).
- An installation without the compiled extension (the portable wheel) still computes offsets, pockets, fills and V-carves with Shapely. Its tool paths are the earlier ones and differ from those of an installation with the extension, in the ways just listed. `KERFKITE_POLYGON_BACKEND=shapely` selects that code deliberately.
- GEOS is no longer part of the native core's build: `kerfkite-cam` is built from KerfKite's own source alone, with no download, and the `KERFKITE_WITH_GEOS`, `KERFKITE_SYSTEM_GEOS`, `KERFKITE_GEOS_SHARED` and `KERFKITE_GEOS_URL` options are gone. Shapely remains a dependency of Studio's Python code.

### Fixed
- macOS no longer uses OpenCL. Apple's is deprecated and has no double precision on Apple silicon. On an Intel Mac runner, a relief forced onto its processor device with `KERFKITE_GPU=on` had not finished after 300 seconds, where the threads took 0.7. A stalled run would also have held the lock every relief job takes to ask for the GPU.
- The assistant server's workshop waits 30 seconds for its browser's first answer, as Playwright's launch did, instead of 15. On a busy Windows runner, a browser's first start with a new profile took longer than 15 seconds.
- A pocket with room for the cutter and none for the helix is refused with `The pocket has insufficient room for the cutter and helix radius`. Studio's Shapely code meant to say so and answered `The first input geometry is empty` instead, because an offset that leaves nothing was counted as a place for the helix.
- Drag-knife paths with repeated points. A knife path that crept away from a point in steps shorter than 0.1 nm and then returned to it stopped generation with a division by zero (in Studio's Python; in the browser's offline CAM it gave coordinates that were not numbers and a misleading work-area message). The cause was the rule for dropping repeated points: each point was compared with the point before it in the drawing, kept or not, so the points kept could include the same point twice, a move with no length and so no direction for the blade. The same rule dropped any number of such steps however far they led. A point is now kept only when it is further than 0.1 nm from the last point kept (`studio.operations.knife_points`). Every move the knife makes then has a direction, and the cut is never further than 0.1 nm from the drawing. A path that is a single point once repeats are dropped cannot be cut with a drag knife and is refused with `Knife paths must contain nonzero travel`, as the offline CAM already refused it; Studio used to leave such a path out of the program without saying so, and to answer `min() arg is an empty sequence` when no path was left. A path with no step between zero and 0.1 nm long, which is every ordinary drawing, is cut exactly as before, byte for byte. Studio, the offline CAM and the native core (which declined these paths until the reference was fixed) now agree.
- Phone pairing offers the workstation's routed network address first. It used to offer the numerically lowest address, which on a machine with WSL, Hyper-V or a container bridge is a virtual adapter no phone can reach; the pairing link, and now the QR code, then pointed the phone at it. The other addresses are listed in the address box.
- Pocket: the light navigation bar attribute, which needs API 27, is no longer referenced on API 26.
- Design routes (`/api/geometry`, `/api/extrude`, `/api/artwork-relief` and the other design endpoints) answer malformed bodies with a JSON `400`. Contours that are not lists of finite XY points are rejected before any geometry is built.
- Pocket: every shape can be selected from the drawing preview. New shapes no longer start exactly on top of the previous one, a repeated tap moves to the next overlapping shape, and a tap within 12 dp of an outline counts.
- Machine-control routes of the local server (`/api/connect`, `/api/command`, `/api/run`, `/api/head`, `/api/arm` and the arm follow-ups, `/api/generate`, `/api/phone-monitor`) now answer a malformed or non-object body with a JSON `400` instead of an unhandled `500`.

### Performance
- Large reliefs are prepared 17 to 38 per cent faster on 24 threads or the GPU, because the native core reads the image and builds the paths: on a 24-thread laptop under Windows the benchmark's three reliefs from a 1024-point image take 71, 140 and 174 ms on the threads instead of 98, 179 and 211 ms. `/api/relief` answers the first of them in 94 to 101 ms instead of 203 to 212 ms, since the core writes the JSON. The core's number text, which every preview it writes uses, now writes digits two at a time and multiplies with the processor's 128-bit product: the G-code preview text of the 135,886-line relief benchmark job takes 157 to 162 ms instead of 179 to 232 ms there, and `/api/generate` answers it in 248 to 278 ms instead of 313 to 362 ms, in four runs of each, with the same bytes (`validation/benchmark_relief.py`, `validation/benchmark_routes.py`).
- The native core's test of whether a contour crosses itself, which it makes before a ramp entry or holding tabs, no longer takes time that grows with the square of the contour's length. It tested every pair of segments whose bounding boxes overlap, and for many long segments side by side (a comb of parallel strokes, a fan, a spiral) that is every pair: 20,000 such segments took two seconds and 100,000, the most a job may hold, about a minute. A tree over the segments now leaves out whole groups of pairs that the reference's test is certain to pass, because their boxes are apart or because every end point of one group is clear of, and on one side of, every line of the other. The same contours of 100,000 segments take about a tenth of a second, and a crossing still ends the test at once. The answer is unchanged: it is compared with Shapely's `is_simple` on tens of thousands of random and adversarial lines by `validation/native_core_parity.py`, and with the test of every pair in the core's self-test. The work is counted in fixed units, the same on every machine, and the tests bound the count. Past a fixed count, about a second of work, a contour is declined as not ported and never answered differently, so no input can hold the tool for long.
- The per-move loops of G-code and rotary generation are ported to C++ in the optional native extension (`studio/_gcode_native.cpp`). With it the relief benchmark generates 4.5 times faster and the rotary benchmark 4.4 times faster than the Python loops, with byte-identical programs. Python remains the reference and the fallback; `backend='python'` or `KERFKITE_GCODE_BACKEND=python` selects it.
- G-code generation is 21% to 31% faster and rotary generation 27% faster on the relief benchmark, with byte-identical programs (`validation/benchmark_gcode.py`).
- Packaged screenshots are recompressed losslessly (635 KiB smaller, pixels identical). The two generated artwork images are untouched because re-encoding would invalidate their content credentials.
- Pocket no longer allocates while drawing the preview and computes each shape's outline once.

### Security
- The phone pendant listener is encrypted by default when the `cryptography` package is installed. Studio creates a certificate for each pairing and places its SHA-256 fingerprint in the pairing link; Pocket 0.5.0 accepts only that certificate. **Pocket 0.4.1 and earlier cannot use these links**: tick **Unencrypted pairing** or start with `--monitor-plaintext` until the phone is updated. The desktop installers do not yet bundle `cryptography` and continue to use HTTP.
- The desktop installers now include `cryptography`, so an installed Studio encrypts the pendant without a further step. Intel macOS receives 48.0.1, the last release published for it; the other targets receive 50.0.2.
- `/api/command` accepts only `action`, `axis`, `distance` and `feed`; any other field is refused before the controller is called.
- The local session token is compared in constant time.

### Development
- The **Build the desktop programs and installers** workflow (`native-programs.yml`) makes a whole release on hosted runners. It builds the programs and packages each target's installer from its folder: the macOS disk images on macOS, Windows Setup on Linux with Debian's NSIS and the .NET SDK, and the Linux packages on each architecture. It then adds the browser-only packages, the guides, the stock artwork, the assistant skill and a carried Pocket APK, which must carry the Pocket release certificate, and writes `SHA256SUMS.txt` and `SBC-SHA256SUMS.txt`. The Linux folders now carry the GTK window, built on manylinux_2_28 with the programs; the workflow fails if any of their files needs a C library newer than glibc 2.28.
- `validation/check_pinned_results.py` pins the core's results through `kerfkite-cam`, where `check_installed_cam.py` pinned the extension's: every digest the extension recorded (levelling, the polygon operations, helix entries, a V-carve, board isolation, a part with its section and a drawing, a relief on all threads, one thread and the GPU) is reproduced to the byte; continuous integration runs it, and the acceptance fixture, on every platform. Every check runs and each failure is reported. The stock preview's V and drill cutters take the platform's tangent of half their angle, as the reference did; macOS's library rounds the default 60 degrees differently, so the fixture uses 91 degrees, whose exact tangent lies 0.0006 of a unit in the last place from a double.
- The lint gate covers all the Python left, the development tools (`ruff check .`), and the pre-push hook runs the native self-tests. Dependabot no longer updates Python packages.
- The acceptance fixture (`scripts/simulate_studio.py`), the browser lessons, the JavaScript rotary and template tests, the stock-art exporter, the MCP smoke test and the Android emulator, handset and priority-stop workflows drive the native programs. `validation/native_servers.py` starts `kerfkite-studio` and `kerfkite-web` for them, and provides a proxy that records or holds what a phone or the browser editor sends, and the editor's part in a phone Start.
- The native core reads and writes JSON with its own code and no longer contains JSON for Modern C++. JSON numbers are converted by exact integer arithmetic, independent of the C library and the C locale, and floats are written as Python writes them: answers are equal in every value and type to those of the previous build, and differ in text only for floats from 1e15 up to 1e16 (`1000000000000000.0`, formerly `1e+15`) and for the few doubles the old library did not write with the fewest digits. Text nested more than 200 arrays or objects deep, and text after a NUL byte, are now refused as not valid JSON. The `kerfkite-cam` build takes about a third less processor time and the program is 15% smaller. See [Native code](docs/NATIVE.md).
- Pocket builds remove code they never reach (R8, names kept), for debug and release alike. With the QR scanner the debug APK is 115 KB and the unsigned release APK 73 KB; unshrunk, the scanner's library took the debug APK from 56 KB to 358 KB.
- `validation/pairing_qr_check.py` decodes the pairing codes Studio draws with Pocket's decoder, from simulated camera frames.
- A debug build of Pocket installs beside the released app as **Pocket debug** (`au.cncstudio.pocket.debug`), so a change can be tried on a phone without replacing the released app or its projects. The device workflows drive the debug build unless `KERFKITE_POCKET_PACKAGE` names another id.
- `validation/pendant_tls_pin_check.py` checks Pocket's pinning class against a real phone listener with a JDK, without a phone.
- Pocket is versioned 0.5.0 (version code 6).
- `tests/test_design_api.py` covers the design routes (28% to 87% of `studio/design_api.py`). Overall coverage is 86% with the `mcp`, `web` and `step` extras and 76% on a plain install; the pre-push hook enforces a 75% floor when `pytest-cov` is installed.
- Python sources are formatted with `ruff format` (120 columns, existing quote style kept). The change is layout only: the syntax tree of every file is identical before and after. The pre-push hook and `scripts/ci-local.sh` check formatting.
- `scripts/build_help.py` orders the guide sections by file name, so the bundled help is identical whichever machine builds it.
- `validation/android_handset_pendant_workflow.py` runs the pendant sequence on a supervised physical handset.
- Android: Build Tools 35.0.0 is pinned to match the guide.
- Ruff configuration (`pyproject.toml`) covering syntax, pyflakes, likely-bug and security rules for `studio/`; `scripts/ci-local.sh` runs it.
- `scripts/hooks/pre-push`: a fast local gate (lint, Python tests, JavaScript tests) for use while hosted CI is not run on push.
- `dev` extra with the lint and test tools.
- Dependabot version updates for Python, Gradle and workflow actions.
